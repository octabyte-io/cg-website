Cloudgate installs natively: two Node services under systemd (the console and the API), PostgreSQL
on the same machine, Docker as a Swarm of one, and a Traefik container that serves the apps you
deploy. It is not shipped as a container image. The [Self-host page](/self-hosted) has the short
version; this page is the full one. The source is public at
[github.com/octabyte-io/cloudgate](https://github.com/octabyte-io/cloudgate), and each tested
version is published there as a prebuilt download; [Self-hosting Cloudgate](/docs/self-host)
covers the licence.

## What the server needs

| | |
|---|---|
| Operating system | Ubuntu 24.04 or 26.04, freshly installed. Any other release is refused. |
| Processor | x86-64 (amd64). The script stops on anything else. |
| Size | 2 vCPU, 4 GB memory, 40 GB disk. The install was proved on this size, and warns below 4 GB memory or 15 GB free disk. |
| Access | root over SSH |
| Ports open inbound | 22 (SSH), 80 and 443 (your apps), 3000 (console), 4000 (API) |
| DNS | None to start |
| Outbound access | `get.docker.com`, `nodejs.org`, the npm registry, Docker Hub, `api.github.com`, `github.com`, `release-assets.githubusercontent.com`, `s3.amazonaws.com` and `nixpacks.com` |

<Callout type="tip" title="Check the provider's firewall first">
  A cloud firewall in front of the server that blocks 3000 or 4000 looks exactly like a broken
  install. Before you start, run `python3 -m http.server 3000` on the server and open
  `http://<server>:3000/` from your laptop.
</Callout>

## Install Cloudgate

<Steps>
<Step title="Run the install command">

Run one command on the server, as a user who can `sudo`:

```bash
curl -fsSL https://cloudgate.octabyte.io/install.sh | sudo sh
```

It checks the server is Ubuntu 24.04 or 26.04 on x86-64, then installs a **Cloudgate version**:
one tested release, published as a prebuilt download on GitHub. Nothing is cloned or compiled on
the server. It finds the latest signed version, checks the signature on its checksum file against
Cloudgate's public key, which the script carries, downloads the version and refuses it if it does
not match that checksum. It then finds the server's public IPv4 address and hands over to that
version's `deploy/install.sh`, which does the install into `/opt/cloudgate`. The script is the repository's
[`install.sh`](https://github.com/octabyte-io/cloudgate/blob/main/install.sh); download it with
`-o install.sh` instead of `| sudo sh` to read it first.

The address the console uses is `CLOUDGATE_PUBLIC_HOST`. To use a hostname, or an address other
than the detected one, name it: the host alone, with no `https://`, port or path. The console reads
it when it starts, so changing it later is an edit to `/etc/default/cloudgate-console` and
`/etc/default/cloudgate-backend` and a restart.

```bash
curl -fsSL https://cloudgate.octabyte.io/install.sh | sudo CLOUDGATE_PUBLIC_HOST=cloud.example.com sh
```

To install a particular version rather than the latest, name it with `CLOUDGATE_VERSION`
(`v0.3.12` and `0.3.12` both work). A version older than the one installed is refused, because
database migrations only go forward.

```bash
curl -fsSL https://cloudgate.octabyte.io/install.sh | sudo CLOUDGATE_VERSION=v0.3.12 sh
```

<Callout type="note" title="Every version is signed">
  Each published version has a `.sha256.sig` file beside its tarball and `.sha256`. The installer
  checks it with `ssh-keygen -Y verify` before it downloads the tarball. A missing signature, one
  that does not verify, or a checksum file that names another tarball stops the run with nothing
  changed. A release counts as the latest only once its signature is attached. A server without
  `ssh-keygen` gets `openssh-client` from apt first.
</Callout>

The install also saves the server's public IP as **Settings** > **Instance** > **Public address**,
which the free sslip.io Domains for apps on this server are named from. It uses
`CLOUDGATE_PUBLIC_HOST` when that is a public IP, and otherwise asks `api.ipify.org`,
`checkip.amazonaws.com` or `ipv4.icanhazip.com`, with a 5-second limit each. The address is saved
only while the setting has never been set, so a value you saved or cleared is kept.
`CLOUDGATE_PUBLIC_IP=<ip>` names the address instead, for example a private one on a LAN-only
install, and `CLOUDGATE_PUBLIC_IP=none` leaves the setting empty.

Before it downloads anything, the installer warns about what is likely to fail later: another
program on port 80, 443, 3000 or 4000, less than 15 GB free disk, less than 4 GB memory, or a
download host that does not answer. No warning stops the run; `CLOUDGATE_SKIP_PREFLIGHT=1` skips
the checks. Downloads are tried again up to 3 times when the connection drops, and a second run
started while one is under way stops without changing anything.

The installer takes no subcommands. It prints each stage as `==> Downloading Cloudgate 0.3.12`,
`==> Docker` and so on, then a verification block. Every run is logged to
`/var/log/cloudgate/install-<date>-<time>.log` (root only, the newest 10 kept), and a failed run
ends by naming its log.

</Step>
<Step title="Check that it finished">

A good install ends with a verification block like this:

```text
==> Verification
{"status":"ok"}
{"open":true}
console /sign-up: 200
traefik  :80    : 404  (404 = listening)
swarm: active
network: overlay attachable=true
traefik: true traefik:v3.6.7
```

A `404` from Traefik on port 80 is the success case: it is listening and has no app to serve yet.
After a note about backing up the secrets, the run ends with the Cloudgate mark and, beside it,
`Cloudgate 0.3.12 is installed.` and `Open http://<host>:3000/sign-up`. On a re-run of an
instance that already has an owner it says `is running.` and gives the sign-in address instead.

</Step>
<Step title="Claim the instance">

Open `http://<server>:3000/sign-up` and create an account. **The first account owns the
instance**, and sign-up closes behind it. Everyone after that joins by invitation, from
**Settings** > **Members** > **Invite someone**. Without mail set up, the console gives you the
invitation link to send yourself.

</Step>
<Step title="Add this machine as a Server">

Cloudgate can deploy onto the machine it runs on from the start. To also see its shell, Docker and
setup on screen, open **Servers**, press **Add a Server** and point it at the machine's own address
with a key Cloudgate generates. Running setup on the already-installed machine is safe; every step
checks before it acts. See [Servers](/docs/guide/servers).

</Step>
</Steps>

## What the installer sets up

- The Cloudgate version itself, already built, at `/opt/cloudgate`.
- Node from `nodejs.org`, checksum-verified, in Cloudgate's own folder
  `/usr/local/share/cloudgate/node`, so a Node of your own in `/usr/local` is left alone.
- Docker, `docker swarm init` (a Swarm of one), and the `cloudgate-network` overlay network.
- PostgreSQL, with a generated role and password.
- Nixpacks for builds, and OpenTofu with pinned AWS and Google Cloud providers for Cloud accounts
  (about 255 MB to download).
- A `cloudgate` service user, the folder `/etc/cloudgate`, and Traefik's configuration.
- The `cloudgate-traefik` container on ports 80 and 443.
- Two systemd units, `cloudgate-backend` and `cloudgate-console`, that restart on their own.
- `cloudgate-boot-recover`, a unit that runs after every start of Docker and starts Traefik and any
  Compose container whose start failed because the Swarm network was not up yet. See
  [After a reboot](#after-a-reboot).
- ufw, allowing 80, 443, 3000, 4000 and SSH on every port the server's SSH listens on.

Secrets are generated once and kept in `/etc/default/cloudgate-secrets` (readable only by root); a
second run reads them back instead of making new ones.

<Callout type="warn" title="ufw does not protect published ports">
  Docker writes its own firewall rules ahead of ufw. A port you publish later, for example a
  database's external port, is reachable from the internet even though `ufw status` does not list
  it. Treat any published port as public, or block it in the provider's firewall.
</Callout>

## Deploy at an sslip.io address first

You do not need DNS to start. An Application's **Domains** tab can **Generate one for me**: an
sslip.io host such as `web.203.0.113.24.sslip.io`, which resolves to the server's IP, taken from
the public address the install saved. On a public address it is served over HTTPS with a Let's
Encrypt certificate; on a private one it stays plain HTTP. See [Domains](/docs/guide/domains).

## Add a domain later

There are two kinds of domain on a self-hosted instance:

- **Your apps' domains.** Point a DNS record at the server, then add the host on the Service's
  **Domains** tab with **Serve over HTTPS** and **Let's Encrypt**. Traefik gets the certificate.
- **The console's own domain.** **Settings** > **Instance** > **Console domain** serves the console
  on a hostname, over HTTPS. Sign-in there is refused until that origin is trusted: add it under
  **Settings** > **Single sign-on** > **Trusted origins** (needs an Enterprise license) or in
  `TRUSTED_ORIGINS` in `/etc/default/cloudgate-backend`, then restart `cloudgate-backend`. Live
  screens (logs, shells) also need the API on the same hostname: set `CLOUDGATE_API_URL` in
  `/etc/default/cloudgate-console` and restart `cloudgate-console`. No rebuild is needed.
  See [Instance settings](/docs/self-host/instance-settings#serve-the-console-on-a-domain).

<Callout type="limit" title="Plain HTTP until you change it">
  Out of the box the console and API answer on plain HTTP at ports 3000 and 4000, so the session
  cookie crosses the network in clear. Before you give the server a public address, decide whether
  that is acceptable, or close 3000 and 4000 and reach both through one SSH tunnel:
  `ssh -N -L 3000:127.0.0.1:3000 -L 4000:127.0.0.1:4000 root@<server>`, with the instance
  installed with `CLOUDGATE_PUBLIC_HOST=localhost`.
</Callout>

## Upgrade an instance

Run the install command again. It installs the latest published version, or the one
`CLOUDGATE_VERSION` names, reuses the address the last install was given, migrates the database and
restarts both services, keeping your secrets. A run on the version already installed downloads
nothing and only restarts.

```bash
curl -fsSL https://cloudgate.octabyte.io/install.sh | sudo sh
```

An upgrade that changes the version protects you on the way:

- **It dumps the database first**, with `pg_dump`, to
  `/var/backups/cloudgate/pre-<version>-<time>.dump`, readable by root only, and keeps the newest
  three. A dump that fails stops the run with nothing changed. `CLOUDGATE_SKIP_BACKUP=1` skips it,
  for a database too large to dump on every upgrade.
- **It keeps the old version** at `/opt/cloudgate.previous` until the new backend answers its
  health check. If it never does, the run fails, keeps the old version, and prints the dump, the
  old version's path and the steps to go back by hand.
- **It brings Traefik to its version.** When a Cloudgate version moves Traefik, the container is
  replaced with the new image, so ports 80 and 443 drop for a few seconds. A failed image download
  leaves the old one serving.

An instance installed before Cloudgate versions were published, whose `/opt/cloudgate` is a git
checkout, is switched over by the next run on its own: the checkout is moved to
`/opt/cloudgate.checkout-<date>`, the database and settings are kept, and the run says where the
checkout went. Delete it once you have kept anything of yours from it. `CLOUDGATE_REF` is no
longer taken; name a version with `CLOUDGATE_VERSION` instead.

Read the **What to do on upgrade** lines in the repository's
[changelog](https://github.com/octabyte-io/cloudgate/blob/main/CHANGELOG.md) before you upgrade: most
releases need nothing, and the ones that do say exactly what. **Settings** > **Instance** >
**This instance** shows the version an instance runs, and when a newer one is out. The latest is
0.3.12. The [CLI](/docs/cli) needs 0.1.0 or newer, and uploads only the changed files to 0.2.0 or
newer.

The console's **Update and restart** button does not work on a native install, and **Restart
Cloudgate** is refused there: use `systemctl restart cloudgate-backend cloudgate-console`. A queued
Deployment survives a restart; one that was building is cut off and ends as an error.

## After a reboot

Docker tries Traefik and every container on a Swarm network once when it starts, and on a reboot
the Swarm often has not brought `cloudgate-network` up yet, so those starts fail and Docker never
tries again. From 0.3.9, the `cloudgate-boot-recover` unit runs after every start of Docker, waits
up to 3 minutes for the network, and starts exactly the containers whose start failed on it. A
Compose stack you stopped stays stopped. To see what it did on this boot:

```bash
journalctl -u cloudgate-boot-recover -b
```

The install adds the unit to this server. Each Server you added gets it from **Run setup again** on
its **Infrastructure** tab, as setup step 8. Until then, `docker start cloudgate-traefik` and the
stack's **Start** bring things back by hand.

## Back up the instance itself

Cloudgate backs up what you deploy, not itself. The dumps an upgrade takes stay on the same
server, so they do not replace a backup. Keep these four off the server:

- the PostgreSQL database `cloudgate`
- `/etc/default/cloudgate-backend`
- `/etc/default/cloudgate-secrets`
- the folder `/etc/cloudgate`

```bash
su - postgres -c 'pg_dump -Fc cloudgate' > /root/cloudgate-$(date -u +%FT%TZ).dump
tar -czf /root/cloudgate-etc-$(date -u +%FT%TZ).tar.gz /etc/cloudgate /etc/default/cloudgate-*
```

<Callout type="warn" title="The encryption secret cannot be replaced">
  Without `APP_ENCRYPTION_SECRET` from `/etc/default/cloudgate-secrets`, every stored key, password
  and cloud state in the database is unreadable for good. Back up the database and the secrets files
  together, and restore them together.
</Callout>

## Uninstall Cloudgate

Every Cloudgate version from 0.3.2 carries its own uninstall. As root:

```bash
bash /opt/cloudgate/deploy/uninstall.sh
```

It stops and removes the `cloudgate-backend` and `cloudgate-console` services, the
`cloudgate-traefik` container, `/opt/cloudgate` and `/usr/local/share/cloudgate`. **It keeps the
instance**, naming each path: the `cloudgate` database, `/etc/default/cloudgate-*`,
`/etc/cloudgate`, the dumps in `/var/backups/cloudgate` and the logs in `/var/log/cloudgate`. A
later install on the same server is then the same instance. Apps you deployed on the server stop
being routed once Traefik goes; their containers are left to you.

`--purge` removes the kept data too, only after you type the instance's public host; any other
answer changes nothing. Docker, PostgreSQL, the Swarm, ufw and the `cloudgate` user stay in place
either way, and the run says so.

## What the install does not do

<Callout type="limit" title="Limits of a self-hosted install">
  - It installs Cloudgate on one server. The Servers you add later are for your apps.
  - There is no self-update. Re-running the script is the upgrade.
  - Nothing is emailed until you set `MAIL_PROVIDER` (SMTP or Resend) in
    `/etc/default/cloudgate-backend`. Without it there are no password-reset emails, and no console
    screen resets another person's password or two-factor.
  - Ports 80 and 443 belong to Cloudgate's Traefik. Nothing else on the server may listen there.
</Callout>
