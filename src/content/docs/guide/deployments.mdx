Every build, cron run, volume backup run and cloud change is a Deployment. You find them in three
places: **Deployments** in the rail (everything you can reach in the Organization), an
Environment's **Deployments** tab, and each Application's or Compose stack's **Deployments** tab.

## What can you do with a Deployment?

- Start one with **Deploy**, or let a push to GitHub start it.
- Read its log live while it runs, or later, and move the log into the Dock.
- Cancel one that is queued, building or held.
- Build the same source again with **Redeploy** after a failure.
- Roll an Application back to an earlier image without rebuilding.

## How do I start and follow a Deployment?

Press **Deploy** on the Application, then watch its **Build output** until the Deployment reads
`done` or `error`.

<Steps>
<Step title="Deploy">
On the Application's **Overview** or **Deployments** tab, press **Deploy**. Cloudgate answers
"Deployment queued. The build starts as soon as a worker picks it up." A push to the tracked branch
of a GitHub source does the same when **Deploy automatically** is on.
</Step>
<Step title="Follow the output">
The **Build output** card streams the log as the build writes it. While it waits it says "Queued.
It starts when a build slot frees up." The Deployments table updates as each step is recorded.
<Screenshot name="deployment-log" alt="A finished Deployment of the web Application: Queued, Started, Finished, Took and the log file, then the build log ending in Image Pushed, the Swarm update to 2 replicas, a passing health check and Docker Deployed" caption="The log streams while the build runs and stays readable afterwards." />
</Step>
<Step title="Check how it ended">
A build ends `done`, `error` or `cancelled`. Press **Open** on its row for the times and the whole
log.
</Step>
</Steps>

<Screenshot name="application-deployments" alt="The Deployments tab of the web Application: the Build output of a queued Deployment with Cancel and Dock, the Deployments table with pending, running and done rows, each with Open, and the Phases of a Deployment card" caption="Newest first, with Cancel on a queued or running build and Open on every row." />

## What are the phases of a Deployment?

A Deployment runs four phases in order: Clone, Build, Push and Update. The **Phases of a
Deployment** card beside the table lists them:

1. **Clone**: the source is fetched at the commit being deployed.
2. **Build**: the builder turns the code into an image. A Docker image source skips this.
3. **Push**: the image goes to the registry if one is set; otherwise it stays on the Server that
   built it. A Docker image source pushes nothing.
4. **Update**: the Swarm service is updated, and the Deployment waits for its tasks to run. The log
   ends with one of three marks: ✅ the tasks are running and it is done; ❌ Swarm rolled back to
   the previous spec and the Deployment failed, so the one before it is serving; ⚠️ the wait ran out
   with neither, so it is done but its tasks were never confirmed running.

A build is one phase of a Deployment, which is why a failed Deployment can leave the previous one
serving.

## What does each status mean?

A Deployment is `pending` while queued, `running` while it builds and releases, and ends `done`,
`error` or `cancelled`; `held` waits for a Plan.

| Status | Meaning |
|---|---|
| `pending` | Queued, waiting for a build slot. |
| `running` | Building or releasing now. |
| `done` | Finished. A Cron service's run reads **succeeded**. |
| `error` | Failed; the log says where. A Cron service's run reads **failed**. |
| `cancelled` | Stopped before it finished. A run its Cron service's Stop ended reads **stopped**. |
| `held` | Waiting for a Plan: the push changed both the code and the Service's entry in a repository-kept `cloudgate.yaml`. |

A `held` build continues when the Environment's [Plan](/docs/guide/project-config) is applied or
dismissed. **Build now with saved settings** on its row builds the code at once with the settings
already saved, ignoring the config change.

## Read a Deployment log

Press **Open** on a row of the **Deployments** tab, or **Log** on the Deployments page, to open the
Deployment in a dialog: **Queued**, **Started**, **Finished**, **Took**, the **Log file** path and
the log itself.

| Control | What it does |
|---|---|
| **Dock** | Moves the log into a panel along the bottom of the console. A live log keeps following there while you go to other pages. The Dock holds four logs. |
| **Show the Dock** / **Read it here too** | Shown in place of a docked log, to jump to it or read it on the page as well. |
| **Reload** | Reads a finished log again. |
| **Explain this log** | Sends the finished log's lines to your AI provider and shows what it thinks went wrong. Shown only when an AI provider is set up. |

The words beside a live log say how the stream is doing: **Connecting to the build…**,
**Streaming**, **Reconnecting…**, **Stream closed**, **Stream refused** or **Not connected**. If
the browser cannot open the stream, the build is unaffected and its log can be read once it
finishes. An empty log usually means the build was refused before it wrote anything; the reason is
on the Deployment.

## How does the build queue work?

Without an Enterprise license, each Server builds one Deployment at a time and the others wait as
`pending`. With a license, the instance builds up to its **Concurrent builds** setting at once
(self-hosted, Settings > Instance).

A queued Deployment survives a restart of Cloudgate. A running one is cut off by a restart, ends as
`error` and is not started again: deploy again when Cloudgate is back.

## Cancel a Deployment

Press **Cancel** on a `pending`, `running` or `held` Deployment, on the output card or its row.
Cloudgate says "The build was cancelled before it started", "The build was stopped", or, for a cron
run, "The run was cancelled. Its timetable keeps going."

A Cloud run (an OpenTofu change in AWS or Google Cloud) has **Stop the run** instead. It asks first:
OpenTofu is interrupted and killed if it has not stopped within 5 minutes, the Deployment ends as an
error that says you stopped it, and changes made so far stay in the cloud for the next deploy to
pick up. A cloud deploy that stopped for review has **Review the open plan**.

## Rebuild after a failure with Redeploy

When the last Deployment failed, the Overview's banner has **Redeploy**: it builds the source the
Application already has again, with no new commit, and records the attempt as a rebuild. "Rebuild
queued." Variable changes also need a Deployment to reach the container; press **Deploy**.

## Filter every Deployment on the Deployments page

**Deployments** in the rail lists every Deployment of the Applications and Compose stacks you can
reach, across Projects.

<Screenshot name="deployments-list" alt="The Deployments page over 7 days: All 109, Running 1, Done 100 and Error 6, Every Project, and a table of Deployments, backups and cron runs with status, Service, duration, time and Log" caption="Pick a time range and a status; the counts on each status follow the range." />

| Control | What it does |
|---|---|
| Time range | **Last hour** (the default), **6 hours**, **24 hours** or **7 days**, by when each was queued. |
| Status | **All**, **Running**, **Done** or **Error**, each with its count in the range. |
| **Every Project** | Narrows to one Project. Shown when more than one Project has Deployments. |
| **Every service** / **Services you have opened** | Narrows to the Services in your recents. |
| **Refresh** | Reads the list again. |

Each row names the Service (linked to its Deployments tab) with its Project and Environment, or the
kind of run (**Scheduled run**, **Volume backup**, **Database backup**, **Environment network**,
**Cloud run**). **Log** opens its log in a dialog without losing your filters. The page reads a
bounded number of pages; when older Deployments in the range are left out, the count says so. To
cancel, open the Service's own Deployments tab.

## Roll back to an earlier Deployment

The **Rollbacks** tab puts an Application on an earlier version without rebuilding it.

<Steps>
<Step title="Turn on rollback points">
In **Keep rollback points**, turn on **Capture a snapshot on every successful Deployment** and press
**Save changes**. Each snapshot keeps a tagged copy of the image on the Server. Turning it off later
keeps the snapshots already taken.
</Step>
<Step title="Pick a point">
**Rollback points** lists each one's **Version**, **Image**, **Built from** and **Captured**.
<Screenshot name="application-rollbacks" alt="The Rollbacks tab of the web Application: Keep rollback points switched on, and 15 rollback points from v15 down, each with its image, branch, capture time, Roll back and Delete" caption="One point per successful Deployment while the switch is on." />
</Step>
<Step title="Roll back">
Press **Roll back** on the point. The dialog shows the image, branch, builder and capture time, then
press **Roll back to v4** (its version). The Swarm service is updated in place in seconds.
</Step>
</Steps>

What a rollback does and does not change:

- It restores the image and its service spec. It writes **no Deployment**, so it does not appear on
  the Deployments tab.
- A snapshot holds no secrets, so the Application keeps the variables, build arguments and
  credentials it has now.
- Its settings are not changed, so the next Deployment builds from them as they are now. To stay on
  the old version, change the source first.

<Callout type="warn" title="Deleting a rollback point">
**Delete** on a point deletes its image from the Server, not just the row. Getting that version
back means building its commit again. Nothing running changes.
</Callout>

### Rollbacks in a Cloud account

A static site in a Cloud account (built with **Static files**) keeps each Deployment's files in the site's bucket as a rollback point when
**Keep the files of every Deployment as a rollback point** is on. Rolling back restores that
version's files and runs as a Deployment, which you follow on the Deployments tab. Any other
Service in a Cloud account has no rollback yet: the tab says "Rollback is not available on AWS yet"
(or Google Cloud), because each deploy keeps only its live image. Deploy again to change what runs.

## What you cannot do

- Roll back to a Deployment made before rollback points were on.
- Roll back a database or a Compose stack: they have no Rollbacks tab. Use
  [backups](/docs/guide/backups) for data.
- Undo what a Deployment did to your data: a rollback changes the image, never a database.
- Cancel from the Deployments page: use the Service's own tab.
- Restart a Deployment cut off by a Cloudgate restart; deploy again instead.
- Read a Deployment log older than 90 days.

<Callout type="limit" title="Who can do it">
Deploying, cancelling and **Build now with saved settings** need the create or cancel action on
Deployments, which the member role has for the Services it is granted. The rollback switch needs
the update action on Services. Agents with the Operator role can deploy and cancel through
[MCP](/docs/mcp).
</Callout>
