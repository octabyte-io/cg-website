The examples use a bucket named `media` in the `storefront` Project and the `web` Application
that stores customer images in it.

## What can you do with a bucket?

- Add a bucket in the [Project config](/docs/guide/project-config) and link it to any number of
  Services.
- Read the same six Outputs on every target, so one codebase works on a Server and in a cloud.
- Allow web pages to upload straight from a browser.
- Give a bucket on a Server its own Domain, and rotate its key.
- Back up and restore a bucket on a Server.
- Use a bucket you already have in a cloud, as given.

## How do I add a bucket?

A bucket is created only by the Project config. The console has no add button for it.

<Steps>
<Step title="Write it in the Project config">
Add an entry with `kind: bucket`, and link its Outputs under the Service that uses it:

```yaml
version: 1
services:
  media:
    kind: bucket
  web:
    kind: web
    source:
      github: northwind/storefront
    env:
      - S3_BUCKET: media.name
      - AWS_REGION: media.region
      - S3_ENDPOINT: media.endpoint
      - S3_FORCE_PATH_STYLE: media.path_style
      - AWS_ACCESS_KEY_ID: media.access_key_id
      - AWS_SECRET_ACCESS_KEY: media.secret_access_key
```
</Step>
<Step title="Review and apply the Plan">
Save the config in Cloudgate, or push it to the Config branch. Each Environment shows a Plan that
creates the bucket; press **Apply**.
</Step>
<Step title="Deploy the Service">
Deploy `web`. Each linked value reaches its container at the deploy and is never saved on the
Service.
</Step>
</Steps>

The bucket then appears on its Environment's **Services** tab; its row opens the bucket's screen.

## What does each Output hold?

Every bucket hands out the same six Outputs on every target, so one codebase works on a Server and
in a cloud; only the values differ:

| Output | On a Server | On AWS |
|---|---|---|
| `name` | the bucket's real name, made by Cloudgate | the same |
| `region` | `us-east-1` | the Environment's region |
| `endpoint` | the bucket's Domain while it has one, else its internal URL | `https://s3.<region>.amazonaws.com` |
| `access_key_id`, `secret_access_key` | the bucket's key | no value: the Service's task role gives access |
| `path_style` | `"true"` | `"false"` |

There is no `url`. On Google Cloud the bucket is a Cloud Storage bucket with its own key, shared
by every Service that links it.

<Callout type="warn" title="Do not pass the keys to your S3 client by hand on AWS">
On AWS the key variables are left unset, not set to empty. An app that builds its client with
`credentials` from those variables gets an undefined key. Leave `credentials` out and let the SDK
find the task role, so the same code works everywhere.
</Callout>

## What is on a bucket's screen?

A bucket has one screen, with no tabs: everything about it beyond these cards is in the Project
config. The header shows its status, a `bucket` chip (and `existing` for a bucket made outside
Cloudgate) and **Delete**.

<Screenshot name="bucket-screen" alt="The screen of the media bucket, with its real name, region, key card and domains" caption="The oldest Domain is the bucket's endpoint." />

| Card | Shown when | What it holds |
|---|---|---|
| **Bucket** | Always | **Real name** (with copy), **Config name**, **Runs on** (Server) or **Cloud account**, **Region**, **Key** (set or not made yet) or **Access** (on AWS: each Service's own task role, no key), the **Swarm service** on a Server, **Environment** and **Created**. |
| **Access** | An existing bucket on Google Cloud | Whether its key reaches the bucket, the key's service account, when it was checked, and the grant command to run. |
| **Key** | On a Server or Google Cloud | **Rotate key** and **Last rotation**. |
| **Domains** | On a Server | Where the bucket answers S3 requests from the internet. |
| **Browser uploads** | A bucket Cloudgate made | The web origins trusted to upload from a browser. |
| **Volume backups** and **Restore** | On a Server | Tarballs of the bucket's volume. |

If the bucket was destroyed by a Plan or belongs to another Organization, the screen reads "This
bucket is not here".

## How do I let a browser upload to the bucket?

On **Browser uploads**, enter the origin as a browser sends it, such as
`https://shop.northwind.example`, with no path, and press **Add origin**. **Remove** takes one off.
The list starts empty, which means no browser can upload. Each origin may read, upload and see an
upload's ETag; the bucket's own key is never sent to a browser.

<Screenshot name="bucket-browser-uploads" alt="The Browser uploads card of the media bucket with two trusted origins, https://shop.northwind.example and https://www.northwind.example, and the Origin field" caption="Origins are scheme and host, with an optional port, and no path." />

An existing bucket has no **Browser uploads** card: its CORS rules are yours to set in the cloud.

## How do I give a bucket on a Server a Domain?

A bucket on a Server is reached only from that Server until you press **Add a domain** on its
**Domains** card. Presigned URLs and browser uploads need it: a browser cannot reach the internal
URL. The oldest Domain is the bucket's `endpoint`. **Edit** and **Remove** work as on any Domain:
see [Domains and TLS certificates](/docs/guide/domains). Adding one needs the `domain: create`
permission.

## How do I rotate a bucket's key?

Press **Rotate key** on the **Key** card and confirm. On a Server, Garage makes a new key, read and
write on this bucket only; on Google Cloud, Cloudgate makes a new HMAC key for the bucket's own
service account. Every Service that links the key is then deployed again with it, while the old key
keeps working. Only once every redeploy succeeded is the old key removed. If one fails, the
Services are put back on the old key, the new one is removed, and the card names the Service.

<Callout type="warn" title="Rotating redeploys">
Every Service that links this bucket's key is deployed again. Plan it like a deploy. The button is
off until the bucket's first deploy has made a key, and while a rotation runs.
</Callout>

## Where does a bucket live?

Where its Environment deploys: in a Garage container on a Server, in S3 on AWS, or in Cloud Storage
on Google Cloud.

| Target | What Cloudgate makes |
|---|---|
| Server | its own Garage storage container and volume, S3-compatible |
| AWS | an S3 bucket, versioning off, Block Public Access on; no key |
| Google Cloud | a Cloud Storage bucket with its own service account and key |

On AWS a presigned URL is signed with the task role's short-lived credentials, so it stops working
when they expire. Make one just before it is used.

## Can I use a bucket I already have?

Yes, in a Cloud account. When a Plan would create a bucket, choose **Use an existing bucket** on
that line and enter its **Bucket name** as the cloud's console lists it. A bucket Cloudgate made,
for any Environment, is refused. Cloudgate looks it up at every Plan and never changes it or its
files. On Google Cloud its key is one Cloudgate makes for it, and you grant that key access
yourself: the bucket's **Access** card shows the exact command and checks it.

## How do I delete a bucket?

Remove the entry from the Project config, or press **Delete** on the bucket's screen, type its name
and press **Delete bucket**.

- **A bucket that holds files is kept.** Any file, old version or delete marker counts, and so does
  a bucket Cloudgate cannot read. On a Server its volume stays with the files; in a cloud the
  bucket stays, marked with Cloudgate's tag or labels. Cloudgate forgets it and names it when the
  Delete ends.
- **An empty bucket** is removed: with its volume on a Server, by a Cloud run in a cloud.
- **Also delete its files** empties the bucket, old versions included, then removes it. If
  emptying stops part way, the bucket is kept partly emptied; in a cloud the screen shows
  **Delete incomplete** with **Retry** and **Forget**.
- **An existing bucket** offers **Delete from Cloudgate**: only Cloudgate's records go (on Google
  Cloud, also the key and service account it made), and the bucket and its files stay as they were.

<Callout type="warn" title="Deleted files are gone">
**Also delete its files** removes every file in the bucket. There is no copy unless you made a
[volume backup](/docs/guide/backups#how-do-i-back-up-a-volume).
</Callout>

## Who can change a bucket?

Anyone granted the bucket can rotate its key and change browser origins; deleting it takes an owner
or an admin.

| Action | Needs |
|---|---|
| Rotate the key, add or remove browser origins | `service: update` (owners, admins and members granted the Service) |
| Add a Domain | `domain: create` |
| Delete the bucket | `service: delete` (owners and admins); off while a Project config kept in a repository describes it |

## What you cannot do

- Create a bucket from a console button: use the Project config.
- Link a bucket in another place: a Service and its bucket must be on the same Server, or in the
  same Cloud account and region. The Plan refuses it and names the variable.
- Use a key on AWS: access is the Service's own role.
- Change a bucket's policy, CORS or versioning from a linked Service.
- Count on a presigned URL on AWS lasting more than about an hour.
