The examples back up the PostgreSQL database `orders-db` and the `uploads` volume of the `web`
Application in `storefront` to a Destination named `northwind-backups`.

## What can you back up?

Databases on a Server (except Redis), named volumes of Applications and Compose stacks, and
buckets on a Server. A database in AWS or Google Cloud is backed up by the cloud.

| What | Where you set it up | What it writes | Restore |
|---|---|---|---|
| PostgreSQL, MySQL, MariaDB, MongoDB on a Server | the database's **Backups** tab | a compressed dump | **Restore** on a dump |
| libSQL on a Server | the database's **Backups** tab | a tar of its data directory | **Restore** on a dump |
| Redis on a Server | nothing: no dump command | | |
| A named volume of an Application | its **Volume backups** tab | a tarball | **Restore a volume** |
| A Compose stack's volumes | its **Volume backups** tab, one volume or **The whole stack** | tarballs, one moment at a time | **Restore a volume**, or restore a moment |
| A bucket on a Server | the bucket's screen | a tarball of its volume | **Restore a volume** |
| A database in AWS or Google Cloud | the cloud keeps it; set retention on **Backups** | snapshots or backups in the cloud | in the cloud's console |

Nothing else copies data off a Server: a Deployment leaves volumes where they are, and losing the
Server loses them unless a backup has run.

<Callout type="note" title="Server backups of a bought Server are something else">
On the Hosted instance, a Server bought from Cloudgate can keep **Server backups**: copies of its
whole disk, listed on its **Bought Server** tab with **Back up now** and **Restore**. A Server
backup puts the whole machine back as it was; the dumps and volume backups on this page copy one
database or one volume to your own Destination. See [Bought Servers](/docs/guide/bought-servers).
</Callout>

## What is a Destination?

A **Destination** is an S3-compatible bucket that backups are written to. Destinations belong to
the whole Organization and every Project uses the same list; you choose one per schedule. Cloudgate
reaches it with rclone, so AWS S3, MinIO and other S3-compatible providers work.

<Steps>
<Step title="Open Destinations">
Open **Settings** > **Destinations** and press **Add a destination**.
<Screenshot name="settings-destinations" alt="The Destinations settings page listing the northwind-backups bucket with its name, bucket, endpoint and region" caption="Destinations are shared by every Project in the Organization." />
</Step>
<Step title="Describe the bucket">
Fill in **Name** (what it is called in Cloudgate), **Endpoint** (with its scheme), **Region**
(empty if your provider has none), **Bucket**, **Provider** (rclone's provider name, such as `AWS`
or `Minio`; empty lets rclone work it out), **Access key** and **Secret access key**. The secret
is stored encrypted and never shown again.
</Step>
<Step title="Test and save">
Press **Test connection**, then save.
</Step>
</Steps>

<Callout type="tip" title="Keep backups off the machine">
A Destination with another provider, or in another region, survives losing the Server the data is
on. That is the point of writing backups off it.
</Callout>

A Destination that a database schedule or a volume backup still uses cannot be deleted: the refusal
names each one. Remove or change those first.

## How do I schedule database dumps?

Add a schedule on the database's **Backups** tab, with a Destination and a cron expression, then run
it once to check it:

<Steps>
<Step title="Open the Backups tab">
Open the database, such as `orders-db`, and its **Backups** tab. With no Destination yet, the empty
state offers **Connect a destination**.
</Step>
<Step title="Add a schedule">
Under **Scheduled dumps** press **Add a schedule** and fill in the fields below.
<Screenshot name="database-backups" alt="The Backups tab of orders-db, with one daily 03:00 dump to northwind-backups keeping 14, and the Dumps in the destination card" caption="The dumps are read straight from the bucket once you choose a destination." />
</Step>
<Step title="Run it once">
Press **Run now** on the row. The dump is handed to the engine; whether it finished, and its log,
is on the **Deployments** page as a **Database backup**, and the file appears under **Dumps in the
destination**.
</Step>
</Steps>

| Field | What it does | Default and notes |
|---|---|---|
| **Database** | The database inside this engine to dump. | Starts as the **Database name** the engine was created with. For MongoDB you must name one; for libSQL it names the file. |
| **Destination** | Where the dumps are written. | Required. |
| **Prefix** | The path in the bucket, under the database's own folder. | Required. A run writes `<bucket>/<service name>/<prefix>/<time>.sql.gz`. |
| **Cron expression** | When it runs: minute, hour, day of month, month, weekday. | `0 2 * * *`, every day at 02:00. The form reads it back in words. |
| **Keep the newest** | How many dumps to keep under the prefix; older ones are deleted after each successful run. | Empty keeps every one, and the bucket keeps growing. |
| **Run on the cron** | Off keeps the schedule without firing it. | On. |

Files end in `.sql.gz` for PostgreSQL, MySQL and MariaDB, `.bson.gz` for MongoDB and `.tar.gz` for
libSQL. MySQL dumps and restores run as root, not as the application user. libSQL has no dump
tool, so its backup is a tar of the whole data directory.

### Manage a schedule

Each row shows **When** (the cron and its reading, "paused" when off), **Database**, **Written to**
(the Destination and the full path) and **Kept**. **Run now** dumps at once; **Pause** and
**Resume** stop and restart the cron; edit the row to change any field. Removing a schedule stops
it firing and leaves the dumps already written in the bucket, where a restore can still use them.

### Find a dump in the destination

The **Dumps in the destination** card lists files straight from the bucket. Choose a
**Destination**, then narrow **Path in the bucket**, which starts at the database's own folder.
Folders open when you press them; at most 100 objects come back per listing, and **Refresh** reads
again.

## How do I restore a database dump?

Press **Restore** on a dump under **Dumps in the destination**, name the database it goes into, and
confirm with the database's name.

<Callout type="warn" title="A restore replaces what is in the database now">
The restore command drops as it goes and takes no copy first. It cannot be undone. Take a fresh dump
before you restore if you might need what is there.
</Callout>

<Steps>
<Step title="Find the dump">
On the **Backups** tab, under **Dumps in the destination**, choose the Destination and press
**Restore** on the file.
</Step>
<Step title="Choose the dump">
The **Restore into orders-db** dialog opens on **Choose the dump**, showing the file, its key, the
Destination and the bucket. Press **Continue**.
</Step>
<Step title="Name the database">
Name the database inside the engine that the dump goes into; it starts as the engine's **Database name**.
For MongoDB, that database's collections are dropped and replaced. A name the dump does not expect
fails inside the engine. Press **Continue**.
</Step>
<Step title="Replace its contents">
Check **From**, **Into**, **On** and **Engine**, type the database Service's name (`orders-db`) and
press **Replace the contents**.
</Step>
</Steps>

## How do I back up a volume?

Volume backups copy a named Docker volume off its Server as a tarball. They are on the
**Volume backups** tab of an Application (an AI model included) and of a Compose stack on a
Server, and on the screen of a bucket on a Server.

<Steps>
<Step title="Open Volume backups">
Open the Application, such as `web`, and its **Volume backups** tab.
<Screenshot name="volume-backups" alt="The Volume backups tab of web before any backup is added, with the Volume backups list, the Run history card and the Restore card" caption="Add a backup and its runs show up under Run history, including the ones the cron fires." />
</Step>
<Step title="Add a backup">
Press **Add a backup** and fill in the fields below.
</Step>
<Step title="Run it now">
Press **Run now** on the row to check it. The outcome lands in the run history below the list.
</Step>
</Steps>

| Field | What it does | Notes |
|---|---|---|
| **Name** | What the backup is called, such as `Nightly uploads`. | |
| **Volume** | The named Docker volume to tar. | The Advanced tab's mounts table lists an Application's volumes. An AI model's weights volume is refused: the weights are downloaded again. On a bucket it is the bucket's own volume. |
| **Destination** | Where the tarballs go. | |
| **Prefix** | The path in the bucket. | |
| **Cron expression** | When it runs. | Five fields, such as `0 2 * * *`. |
| **Keep the newest** | How many tarballs to keep; older ones go after each successful run. | Empty keeps all. |
| **Stop the service while the backup runs** | Stops it for the tar and starts it again afterwards. | Use it for a volume written to all the time: a tar taken mid-write may not restore. |
| **Enabled** | Off keeps the backup without firing it. | |

Each row shows **Name**, **Volume** (or **The whole stack**), **When** (the cron in words, and
"stops the service first" or "stops the stack first" when it does), **Written to** (the Destination
and the path in its bucket) and **Keeps**. **Run now** is a button on the row; **Restore**, **Edit**
and **Remove** are in the row's menu. Removing a backup stops it firing and leaves its tarballs in
the bucket, where a restore can still use them.

### Back up a whole Compose stack

On a Compose stack, the form asks first what to **Back up**:

<Screenshot name="compose-volume-backup-add" alt="The Add a backup dialog on a Compose stack with Back up set to The whole stack, a Destination, a prefix, a cron expression and Stop the stack while it runs switched on" caption="The whole stack is the default: one run copies every named volume from the same moment." />

- **The whole stack** copies every named volume in one run, so the database's volume and the files
  come from the same moment. **Stop the stack while it runs** stops every service once for the copy
  and starts them again, even when a tar fails. It starts on when a service runs a `postgres`,
  `mysql`, `mariadb` or `mongo` image, and while the stack's services are not known yet.
- **One volume** asks for the **Service** that mounts it and the **Volume** (its mounted named
  volumes, or **Other volume** and its full **Volume name**). Bind mounts are not listed.

On **The whole stack**, **Keep the newest** counts whole moments: older moments under the prefix are
deleted after each successful run, every volume of a moment together.

<Screenshot name="compose-volume-backups" alt="The Volume backups tab of a Compose stack listing a whole-stack backup, with The whole stack in its Volume column, Run now on the row and the Run history card below" caption="A whole-stack backup's row menu holds Restore, which puts back a whole moment." />

A backup cannot change what it backs up after it is created. A Compose stack in a Cloud account has
no **Volume backups** tab: there is no Server to copy its volumes on. On a swarm stack, only the copy
of a volume on the stack's own Server is backed up, and the tab says so.

### Why does the tab say the stack hasn't deployed yet?

Cloudgate learns a stack's named volumes from its last successful deploy, so deploy the stack once
before you back it up. Until a deploy has run, the tab says "This stack hasn't deployed successfully
yet, and its volumes are read from its first deploy", **One volume** offers only **Other volume**,
and a whole-stack run is refused with the same reason. A stack last deployed on a Cloudgate older
than 0.3.13 says it "last deployed before Cloudgate recorded a stack's volumes": redeploy it once and
its volumes appear. A stack whose services mount no named volume has nothing for **The whole
stack** to copy.

## How do I restore a volume?

Stop what uses the volume, pick a tarball from the Destination, confirm the volume's name, then start
the Service again:

<Steps>
<Step title="Stop what uses the volume">
A volume cannot be restored while any container, running or exited, references it. **Stop** the
Application; for a Compose stack, use **Remove containers**. A bucket is stopped and started again
by the restore itself. A whole-stack restore removes the containers for you: see
[Restore a moment](#restore-a-moment-of-a-whole-stack-backup).
</Step>
<Step title="Start the restore">
On the **Restore** card press **Restore a volume**. On an Application or a one-volume backup of a
stack, **Restore** in the backup row's menu opens the same dialog on that backup's path.
</Step>
<Step title="Choose the tarball">
Choose the **Destination**, narrow the **Path in the bucket**, and pick the **Tarball** from the
list, newest first, read straight from the bucket, with its size and age and **Newest** on the
latest. Each tarball shows its file name, whose time says which backup it is; the full path is on
hover. Press **Next**.
</Step>
<Step title="Confirm the volume">
Check or type the **Volume** it is unpacked into, on the Server the Service runs on. Press **Next**.
</Step>
<Step title="Replace its contents">
Check the **Volume**, the **Tarball** (its file name whole, under its folder) and **On**, type the
volume's name and press **Replace** followed by the volume name.
</Step>
<Step title="Start it again">
**Start** the Application, or the stack.
</Step>
</Steps>

<Callout type="warn" title="The volume's current contents are replaced">
A volume restore keeps no copy of what was in the volume. Only tarballs still in the Destination
are offered: a backup that keeps the newest five has already deleted the rest.
</Callout>

### Restore a moment of a whole-stack backup

For a **The whole stack** backup, **Restore** in the row's menu opens **Restore a moment of**
followed by the backup's name. Pick a moment (its time and the volumes it holds), type the stack's
name and press **Restore this moment**. It runs as one restore, with each step shown as it goes:
**Remove containers** (**Stop** on a swarm stack), **Restore** for each volume in name order, then
**Start**, with the **Restore output** log below. Every volume of that moment is replaced together,
with no copy of what was there. If a volume fails, the restore stops there, the stack stays stopped,
and the steps after it read "not run". A backup that has not run yet has no moment to offer.

## Backups of databases in AWS and Google Cloud

A database in a Cloud account has no dump schedules: "Dump backups to a Destination are Server-only
for now." Its **Backups** tab reads what the cloud keeps, live:

- **Retention**, with the new value "after the next Cloud run" while a change is waiting.
- **Earliest restorable** and **Latest restorable**, where the cloud reports them.
- The name and region in the cloud, and a table of **Snapshots** (or **Backups**) with their kind
  (**Automatic** or **Kept**), when they were taken, status and size.
- **Open in the RDS console** (or the ElastiCache or Google Cloud console). A restore there makes a
  new instance.

Below it, one card sets the retention in days:

| Database | Card | Range |
|---|---|---|
| RDS (PostgreSQL, MySQL) | **Backup retention** | 1 to 35; 0 is refused, because it turns off automated backups and point-in-time restore |
| ElastiCache (Redis) | **Snapshot retention** | 0 to 35; 0 turns snapshots off |
| Cloud SQL (PostgreSQL, MySQL) | **Backup retention** | 1 to 365; point-in-time recovery is on beside them |
| Memorystore (Redis) | **Backup retention** | 0 to 365; 0 turns backups off |

Saving changes nothing in the cloud until the next Cloud run applies it; **Check for changes** to
see it in the Plan. Deleting a cloud database keeps a final snapshot unless you ask to delete its
data too: see [Databases](/docs/guide/databases#how-do-i-stop-rebuild-or-delete-a-database).

## Who can do what?

Owners and admins manage Destinations. Anyone granted a Service can run and restore its backups,
but choosing a Destination or listing its files needs read access to Destinations.

| Action | Who |
|---|---|
| Add, edit, test and delete a Destination | Owner or admin |
| See, run, pause, edit and remove dump schedules and volume backups | Anyone granted the Service, owners and admins |
| Restore a dump or a volume | Anyone granted the Service, owners and admins |
| Pick a Destination, or list the dumps and tarballs in one | Anyone who can read Destinations: owners, admins, or a custom role that grants it |
| Change cloud retention | Anyone who may change the Service (`service: update`) |

The built-in member role can work with backups of the Services it is granted, but it cannot read
the Organization's Destinations, so the Destination picker shows the refusal and the dump listing
stays empty. An owner or an admin can add the schedule for them.

Two backups or restores of the same volume never run at once: the second is refused with a 409
naming the busy volume, and a scheduled backup waits its turn. **Remove containers** on a Compose
stack is refused the same way while a backup or restore holds one of its volumes: "Volume '...' is
busy: a volume backup, a restore or Remove containers holds its lock — try again once that
finishes."

## What you cannot do

- Dump Redis, or schedule dumps for a database in a Cloud account.
- Restore a cloud database from the Cloudgate console.
- Restore a volume while a container still references it.
- Back up the volumes of a Compose stack that runs in a Cloud account.
- Count on a Deployment to back anything up.
