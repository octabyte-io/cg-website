The examples use the `web` Application in the `production` Environment of `storefront`, its
database `pg-main`, and a Redis URL kept once for the whole Project.

## What you can do

- Keep variables on a Project, an Environment and each Service.
- Share one value across Services by referencing it by name.
- Link another Service's **Output**, such as a database's `url`, as a **wired variable**.
- Hide values whose names look secret, and reveal them when you need to.
- Set build arguments and build secrets for the build only.
- Set a Service's variables from the [CLI](/docs/cli/commands) with `cloudgate vars set`.

## Where variables live

| Level | Where in the console | Who sees it |
|---|---|---|
| Project | Project > **Settings** > **Project variables** | Any Service in any of its Environments, by reference |
| Environment | Environment > **Variables** | Any Service in that Environment, by reference |
| Service | Service > **Variables** | That Service's containers |

**Variables are not inherited.** A Service is deployed with its own keys only. The Service's
**Variables** tab lists what is **Available from the Environment** and **Available from the
Project**, "by reference, not by inheritance".

## Set a Service's variables

<Steps>
<Step title="Open the Variables tab">
Open the Service, such as `web`, and its **Variables** tab.
<Screenshot name="application-variables" alt="The Variables tab of the web Application, with its variables masked and the Wired variables card below" caption="Values whose names look secret stay hidden until you choose Show values." />
</Step>
<Step title="Edit the block">
Press **Edit**, or **Add variables** when there are none. Write one `KEY=value` per line. Lines
starting with `#` are comments and are kept.
</Step>
<Step title="Save and deploy">
Press **Save variables**, then deploy the Service. A change here needs a Deployment to take effect.
</Step>
</Steps>

## Share a value across Services

Put the value once on the Project or the Environment, then name it in each Service that needs it:

```text
CACHE_URL=${{project.REDIS_URL}}
API_BASE=${{environment.API_BASE}}
```

The reference is resolved at each deploy. A key on the Project or Environment that no Service names
reaches no container.

<Callout type="warn" title="Removing a shared key fails deploys">
If you remove a key that a Service names, that Service's next Deployment fails rather than running
with an empty value. Check who references it first.
</Callout>

## Link a database or bucket with a wired variable

A **wired variable** is filled in from another Service's Output at each deploy. Nothing stores it
or shows it, so a password rotated at the source reaches the next deploy without anyone copying it.

<Steps>
<Step title="Link a variable">
On the Service's **Variables** tab, find **Wired variables** and press **Link a variable**.
</Step>
<Step title="Pick the Output">
Enter the variable name, such as `DATABASE_URL`, choose the Service `pg-main` and the Output `url`,
and press **Save link**. If the variable already had a typed value, the button reads
**Replace typed value with link**.
</Step>
<Step title="Deploy">
Deploy the Service. When an Output changes later, the console says "A wired variable has a new
value." Deploy again to hand it over.
</Step>
</Steps>

In the [Project config](/docs/guide/project-config) the same link is written under the Service:

```yaml
services:
  web:
    kind: web
    env:
      - DATABASE_URL: pg-main.url
      - S3_BUCKET: uploads.name
```

| Linked Service | Outputs |
|---|---|
| PostgreSQL, MySQL | `url`, `host`, `port`, `user`, `password`, `database`, `ca` |
| Redis | `url`, `host`, `port`, `password`, `ca` |
| Bucket | `name`, `region`, `endpoint`, `access_key_id`, `secret_access_key`, `path_style` |

Every Output is a secret. A Server hands out no `ca`. Remove a link with **Unlink**.

## How secrets are kept

- **Encrypted at rest.** Every variable value is stored encrypted.
- **Masked in the console.** Values whose names look secret (containing `PASS`, `SECRET`, `TOKEN`,
  `KEY`, `AUTH`, `_URL` and similar) are hidden until you press **Show values**. The match is on
  the name.
- **Never returned.** Stored secrets such as a database password or a registry token come back from
  the API only as "set" or "not set".
- **Masked for Agents.** Every tool result an Agent gets, logs included, replaces stored secrets
  with `••••••`.
- **Never in the config.** The Project config lists variable names only, never values.

## Build arguments and build secrets

An Application's **Variables** tab also has **Build arguments** (passed as `--build-arg`) and
**Build secrets**, which are mounted during the build only and end up in no image layer. Use build
secrets for a private package registry token.

## Who can change variables

| Variables | Who |
|---|---|
| A Service's | Members granted the Service (the member role holds `service: update`) |
| An Environment's | Members granted the Environment |
| A Project's | Owner, admin, or a custom role with `project: update` |

A Project write reaches every Environment under it, which is why the member role does not have it.

## What you cannot do

- Make a Service inherit variables: it must name them.
- Change a running container's variables without a Deployment.
- Read a wired variable's value in the console: it exists only in the container.
- Add a new variable name in the console when the Project config is kept in a repository. Values
  stay editable; the name is the file's to add.
- Set Project or Environment variables, build arguments or build secrets from the CLI: only a
  Service's own.
