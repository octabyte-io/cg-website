A Compose stack is one Service built from a `docker-compose.yml`: Cloudgate stores or clones the
file, rewrites it so its Domains and logs work, and applies it with Docker. Pick a Compose stack
when the software already has a compose file, or when several containers belong together. For one
container built from your own code, an [Application](/docs/guide/applications) gives you more:
previews, rollbacks and patches.

## What you can do with a Compose stack

- Write the compose file in the console, or deploy it from GitHub, GitLab, Bitbucket, Gitea or any git URL.
- Apply it as **Docker Compose** on one machine, or as a **Swarm stack**.
- Draft a whole stack from a sentence with **Draft one with AI**, or set one up from a [Template](/docs/guide/templates).
- Route a Domain to any service in the file, and see the exact file Cloudgate deploys on **Converted**.
- Start, stop, restart and remove its containers, act on one container, read its logs and open a shell.
- Set the variables the file substitutes, and edit the config files a Template shipped.
- Back up its named volumes on a schedule and restore them.
- Run it on a Server, or in AWS or Google Cloud on its own Stack VM.

## Who can create, change and delete a stack?

Owners and admins add and delete stacks; any member granted a stack can edit, deploy and run it.

| Action | Who |
|---|---|
| Add a Compose stack, Draft one with AI, delete a stack | Owner or Admin, or a custom role that may create or delete Services |
| Edit the file, source, variables, Domains and settings; Deploy, Start, Stop, Restart; open a shell; volume backups | Any member granted the stack, including the base Member role |
| Read the stack and its logs | Any member granted it |

A control your role cannot use stays visible but off, with the sentence "Your role in this
Organization cannot ..." saying what it would take. See [Members and roles](/docs/guide/members-and-roles).

## Add a Compose stack

<Steps>
<Step title="Open the Environment">
Open the Environment, such as `production` in `storefront`. On its **Services** tab, press
**Add a Compose stack**. The dialog's title is **Add a Compose stack**.
<Screenshot name="compose-create" alt="The Add a Compose stack dialog with A file written here selected, a Name, a Description, Applied as set to Docker Compose and the Server fra-1" caption="On a Server you choose how the file is applied and which Server runs it." />
</Step>
<Step title="Choose where the compose file comes from">
Under **Where the compose file comes from**:

- **A file written here** (the default): stored in Cloudgate and edited on the stack's own screen.
  Nothing is cloned.
- **From a repository**: cloned from a git provider at every Deployment. You connect the
  repository on the stack's screen next.
</Step>
<Step title="Name it">
Enter a **Name**, such as `Storefront workers`, and an optional **Description**. The name is what
Cloudgate shows; the Docker stack name is generated from it once and never changes.
</Step>
<Step title="Choose how and where it runs">
In an Environment that deploys to Servers, pick **Applied as**: **Docker Compose** (brings the file
up on one machine) or **Swarm stack** (schedules it across the Swarm). Then pick the **Server**, such
as `fra-1`. The picker opens on your first Ready Server.

On a self-hosted instance the list also offers **This Cloudgate host**, the machine Cloudgate itself
runs on. Choosing it, or a Server whose address is that machine, shows the Same-machine warning: if
the machine is lost, the stack and all of Cloudgate's records go with it. It warns and never
refuses. The Hosted instance does not offer that machine at all.

In an Environment that deploys to a Cloud account, the dialog shows **Runs on its own Stack VM**
instead: the stack starts at size `medium` (1 CPU, 2 GB) with a 20 GB data disk, and nothing is made
until you apply the Environment's Plan.
</Step>
<Step title="Create it">
Press **Create stack**. The stack opens on its **Overview**, not deployed yet.
</Step>
<Step title="Write or connect the file, then deploy">
For **A file written here**, paste the file into the **Compose file** card and press **Save the
file**. For a repository, press **Change source** on the **Source** card. Then press **Deploy**.
<Screenshot name="compose-overview" alt="The Overview of the plausible Compose stack, with its Identity, Source and Compose file cards and the Stack and Domain cards beside them" caption="Saving the file does not change the running stack: Deploy applies it." />
</Step>
</Steps>

<Callout type="note" title="Every deploy is started by someone">
A stack from a repository is cloned again at each Deployment, but no push deploys a Compose stack.
The **Source** card says so: **Deploys on** reads "Nothing — deploys are manual". Press **Deploy**
when you want the new commit to run.
</Callout>

### Draft a stack with AI

**Draft one with AI**, on the same Services tab, asks your Organization's AI provider for a
complete compose file. It needs a provider under **Settings** > **AI**; without one, or with every
provider turned off, the dialog says so and links there. The dialog **Draft a stack with AI** has
three steps:

1. **Describe**: type **What do you need?**, such as "Deploy Ghost with Postgres" (variants of that
   app) or "a place for the team to write things down" (different projects that solve it). With
   several providers, pick the **Provider**. Press **Ask for suggestions**.
2. **Choose**: pick one of the **Suggestions**. **Back** returns one step.
3. **Read the file**: read the compose file, its variables and the Domains it asks for, pick the
   **Server**, then press **Create this stack**.

The result is an ordinary Compose stack, created but not deployed.

<Callout type="warn" title="Change the made-up secrets">
Every password and secret in a draft was made up by a model. Change the ones that matter on the
stack's **Variables** tab before you deploy it.
</Callout>

### Set up a stack from a Template

**Set up a template**, also on the Services tab, opens the catalogue preset to this Environment.
Most Templates set up a Compose stack. Its facts card then shows a **Template** row, and the
config files it shipped appear on a **Config files** tab. See [Templates](/docs/guide/templates).

## What is on a stack's page?

A stack's tabs are **Overview**, **Converted**, **Containers**, **Logs**, **Shell**, **Config files**,
**Deployments**, **Domains**, **Health**, **Traces**, **Requests**, **Variables**, **Volume backups**
and **Advanced**. Some are absent on purpose:

| Tab | Absent when |
|---|---|
| **Shell** | Your role cannot change the stack (a shell writes inside it). |
| **Config files** | The stack was not set up from a Template that ships config files, or your role cannot read its mounts. |
| **Volume backups** | The stack runs on a Stack VM in a Cloud account. |

Every tab also offers the stack's shell from the **+** on the docked terminal at the bottom of the
console.

### The Stack facts card

Most tabs show a **Stack** card beside them:

| Row | What it says |
|---|---|
| **Status** | idle (never deployed), running, done, error or stopped. |
| **Deployed as** | **Docker Compose** or **Swarm stack**. |
| **Stack name** | The generated Docker name, such as `storefront-workers-4kq2`. It never changes. |
| **Config name** | Its fixed key in the [Project config](/docs/guide/project-config). Renaming the stack does not change it. |
| **Template** | The Template it was set up from, if any. |
| **Source**, **Repository**, **File** | Where the file comes from. A repository stack with no path shows "Found at each deploy". |
| **Network** | Whether routed services join `cloudgate-network` or the stack's own network. |
| **Environment**, **Project** | Links to both. |
| **Server** or **Runs on** | The Server, **This Cloudgate host**, or its Stack VM with machine type and region. On a self-hosted instance, a stack on Cloudgate's own machine shows the Same-machine warning under the card. |
| **Stack VM** | On a Cloud account: Running, Starting, Stopping, Stopped, Not made yet, Not found in the cloud or Unknown. |
| **Created** | When it was made. |

## The Overview tab

The Overview's header shows the stack's name, its kind and Docker name, and the actions: **Open
app** (the first Domain, in a new tab; only once it has one), **Open a shell**, and the lifecycle
buttons described below.

When the last Deployment failed, a banner reads **The last Deployment did not finish.** The build log
on the **Deployments** tab holds the reason: an unparsable file, an image that would not pull, or a
port already taken. Containers that did start keep running; the **Containers** tab shows which.

### Rename a stack or change its description

The **Identity** card holds **Name** and **Description**. Press **Save changes** on the card to keep them. The
Docker stack name stays as it was.

### Change where the compose file comes from

The **Source** card shows the **Type**, **Repository**, **Branch** and **Compose file**. Press
**Change source** and pick one of:

| Source | What it is |
|---|---|
| **A file written here** | Stored in Cloudgate and edited on this screen. Nothing is cloned. |
| **GitHub** | A repository a connected GitHub account can reach. |
| **GitLab** | A project on gitlab.com or your own GitLab. |
| **Bitbucket** | A repository in a Bitbucket workspace. |
| **Gitea** | A repository on a Gitea instance you run. |
| **Any git URL** | Cloned from a URL you give, with an SSH key if it is private. |

For a repository, set the repository, branch and **Compose file** path from the repository's root,
such as `./deploy/compose.yaml`. The **Compose file** box may be left empty (its placeholder is
only an example): each deploy then uses the first of `compose.yaml`, `compose.yml`,
`docker-compose.yaml` and `docker-compose.yml` in the repository's root. The build log says which,
for example "No compose file named: using compose.yaml", and names any others it found but did not
use. With none of them there, the deploy fails with "No compose file named, and none found". A git
provider must be connected first in **Settings**.

<Screenshot name="compose-source-change" alt="The Source card in edit mode with six choices: A file written here, GitHub, GitLab, Bitbucket, Gitea and Any git URL, with GitHub picked and its connection, repository, branch and compose file fields below" caption="Change source switches between a stored file and a repository at any time." />

### Write and check the compose file

For a stored file, the **Compose file** card is an editor. It checks as you type:

- **This is not valid YAML (line n).**: Docker would refuse it the same way, so **Save the file**
  stays off until it is fixed. Unresolvable YAML aliases are caught too.
- **Not set in this stack's variables: NAME (line n).**: Docker would substitute an empty string.
  Set the name on the **Variables** tab, or give it a default such as `${POSTGRES_USER:-ghost}`.

**Save the file** stores it; **Discard changes** drops the edit. Saving changes nothing that runs:
deploy to apply it.

Long lines do not wrap: the editor scrolls sideways inside its own box, so indentation and the line
and column in an error read as written. Turn on the **Wrap lines** switch under the editor to wrap
them; your browser remembers the choice for every editor in the console. Read-only views, such as
the converted file and its diff, always wrap.

<Screenshot name="editor-wrap-lines" alt="The Compose file editor of a stack with a long command line running past the edge and the Wrap lines switch under the editor" caption="Wrap lines is off by default; the switch is remembered for every editor." /> **Expand** opens the editor filling the window, with **Discard** and **Save** in
its top bar and a status line saying whether the YAML is valid; **Back to page** or Esc returns with
the edit kept.

For a repository stack the card shows where the file is read from and nothing to edit: change the
file in the repository, then deploy.

Under the editor, **Services in this file** lists each service the file declares. **Re-read**
reads it again. A repository stack's services can be read only after its first Deployment, because
Cloudgate reads them from the clone on the deploy target.

## Deploy, start, stop, restart or remove containers

The lifecycle buttons sit on the Overview, Containers, Logs and Deployments tabs.

| Button | What it does | Offered |
|---|---|---|
| **Deploy** | Applies the compose file as it is now. Services with a build are built again; an image already on the machine is pulled again only if its `pull_policy` says so. | Always. Off while the file is empty or declares no services. |
| **Start** | Runs the stack again from what is already on the machine (`docker compose up`), with no clone or build. Recreates removed containers. | Docker Compose, when the stack is stopped or any container is not running. |
| **Restart** | Restarts the containers (`docker compose restart`), with no clone or build. | Docker Compose, in place of Start while every container runs. |
| **Stop** | Docker Compose: stops the containers and keeps them. Swarm stack: removes its services from Swarm (`docker stack rm`); **Deploy** recreates them. | Once deployed. |
| **Remove containers** | Removes the containers and keeps the network, the project directory, the named volumes and the stack in Cloudgate. Asks first. | Docker Compose, once deployed. |

When an action is off, a line under the buttons says why: "Nothing of this stack is on its deploy
target yet" before the first deploy, or "This stack's containers are removed" after Remove
containers. A stopped stack stays stopped, after a reboot too. If a request does not come back, the
action may still have run: watch the **Status** on the facts card.

### What Remove containers keeps and loses

The dialog **Remove the containers in ...?** lists what goes: every container of the stack. Named
volumes are kept. Anything a container wrote outside a named volume is lost, and an unnamed volume is
left behind and not re-attached: **Start** gives the service a new empty one.

Use **Remove containers** before restoring a volume: Docker counts an exited container as still using
its volume, so a restore is refused while one is there.

<Callout type="warn" title="Remove unused volumes takes more than this stack's">
**Settings** > **Maintenance** > **Remove unused volumes** clears the unnamed volumes Remove containers
leaves behind, but it removes every volume on the Cloudgate host with no container attached, including a
stopped database's data, whichever Service it belongs to.
</Callout>

## See what Cloudgate deploys: the Converted tab

The **Converted** tab shows how Cloudgate rewrites your file before applying it. Its **What deploying
will change** card lists each change:

- **Traefik labels** on each service a Domain routes into, one router per entrypoint, with an HTTPS
  redirect and path middlewares when the Domain asks for them. A Swarm stack's routing goes into a
  Traefik file on its Server instead.
- The shared network: each routed service joins `cloudgate-network`, or the stack's own network when
  it is isolated.
- **A log cap** (a `json-file` logging block with this instance's size limits) on every service that
  does not declare its own logging.
- On Docker Compose, `restart: unless-stopped` on every service that does not declare a restart
  policy, so the stack comes back after a reboot.

It also shows what would stop a deploy: a Domain that names no service, a Domain routed into a
service the file does not have, or a service that writes `labels:` as a map (write them as a list of
`KEY=value` strings instead).

The card **The file this stack deploys** shows the converted file with **Copy**. For a stored file,
**Changes** shows a one-column diff: a minus line is in your file, a plus line is what the deploy
applies. A repository stack shows only the converted file, and only after its first Deployment.

<Screenshot name="compose-converted" alt="The What deploying will change card of the plausible stack: Traefik labels for stats.northwind.example, the shared network, a log cap, and no restart policy added because every service declares one" caption="Nothing here writes: edit the file on the Overview." />

## Act on one container: the Containers tab

**Containers** lists each service of the file against what Docker runs: **Service**, **State**
(running, created, restarting, paused, exited, dead), **Image**, **Ports** (Docker's own notation: an
entry with `->` is published on the machine, one without is reachable only inside the stack's
network) and, for a Swarm stack, **Node**. **Re-read** reads it again.

Each container Docker reports has an **Actions** menu: **View its output**, **Start**, **Restart**
and **Stop**, then **Kill** under **Immediately** (stops it at once, whatever it was doing). There
is no Remove here: **Remove containers** in the header acts on the whole stack. A declared service
with no container says **Deploy the stack**. On a Stack VM there is no per-container menu; the row
says **Restart the stack instead**.

If the machine cannot be reached, the tab says the containers could not be read, which is not the
same as nothing running.

<Screenshot name="compose-containers" alt="The Containers tab of the plausible stack with its plausible, plausible_db and plausible_events_db services, the Actions menu open on plausible showing View its output, Start, Restart, Stop and Kill" caption="Per-container actions act on one container; the buttons above act on the whole stack." />

## Read a container's logs and open a shell

**Logs** streams one container's live output: pick it under **Container**. It starts with the last
200 lines and follows the tail until you scroll up. **Reconnect** opens the stream again, and the
dock button moves it to the bottom of the console so it keeps running while you move between tabs.
On a Swarm stack, **Read from** also offers **A whole service**, which aggregates every task of one
service.

**Shell** opens `sh` in one running container, picked by its compose service. Leaving the tab ends
the shell unless you dock it first. See [Monitoring](/docs/guide/monitoring) for runtime and access
logs across Services.

## Edit the config files a Template shipped

A stack set up from a [Template](/docs/guide/templates) keeps the Template's config files as file
mounts. The **Config files** tab lists them by path; each shows where it is mounted in the container.
Edit one and press **Save the file**: only that content is written where the stack runs. If the app
reads it only at startup, press **Restart to apply**. On a Swarm stack there is no restart button:
deploy the stack instead.

Edit them here rather than over SSH: a change made on the machine is overwritten later by Cloudgate's
own copy. Saving needs a role that can change the stack and write volumes; restarting needs one that
can deploy.

## Follow a stack's Deployments

**Deployments** lists every attempt, newest first, with **Open** for its log. While a deploy runs,
**Deployment output** streams it above the table; **Follow the newest instead** switches to the
latest one. See [Deployments](/docs/guide/deployments) for statuses and the build queue.

## Give a service in the stack a Domain

Open **Domains** and press **Add a domain**. The dialog asks:

| Field | What it does |
|---|---|
| **Service** | Which service in the compose file the host routes into. Typed by hand when the file could not be read yet. |
| **Host** | The host, such as `shop.northwind.example`, or a generated sslip.io host if you do not own a domain. |
| **Container port** | The port the service listens on inside its container. Cloudgate suggests the first port the file exposes. |
| **Path**, **Strip the path before proxying** | Route only a path, and optionally hide it from the service. |
| **Serve over HTTPS**, **Certificate** | HTTPS and its certificate, such as Let's Encrypt. |

Press **Add domain**. A Domain on a Compose stack is written into the file as labels at deploy, so a
new or changed host is served from the **next Deployment**. Certificates work as they do for
Applications: see [Domains, TLS and CDN](/docs/guide/domains).

<Screenshot name="compose-add-domain" alt="The Add a domain dialog for a Compose stack with Service set to plausible, a Host, the DNS record to create and Container port 8000" caption="A stack's Domain names the service it reaches; it is served from the next Deployment." />

## Set variables for the compose file

**Variables** holds `KEY=value` lines the compose file substitutes, such as `${POSTGRES_PASSWORD}`.
Press **Add variables** (or **Edit**), paste the block and save; **Show values** reveals them.

- On Docker Compose they are written to a `.env` file beside the compose file at every Deployment;
  on a Swarm stack they are set in front of `docker stack deploy`.
- A container receives a variable only if the file passes it, through `environment:` or `env_file:`.
- Cloudgate adds `APP_NAME`, `COMPOSE_PROJECT_NAME` and `DOCKER_CONFIG` (the last only if you did not
  set it).
- Project and Environment variables are never inherited. Reference them by name, such as
  `CACHE_URL=${{project.REDIS_URL}}` or `${{environment.KEY}}`. A reference to a name that is not set
  fails the deploy.
- Values are masked when the key's name looks like a credential.

See [Environment variables](/docs/guide/environment-variables).

## Back up a stack's volumes

**Volume backups** copies a stack's named volumes off its Server to a
[Destination](/docs/guide/backups) on a cron. A Deployment never copies a volume, so nothing else
does. Press **Add a backup** and choose under **Back up**:

- **The whole stack** (the default): a Stack backup, with one schedule and one run. Each run stops
  the stack (when **Stop the stack while it runs** is on), tars every named volume into one folder
  for that moment, and starts the stack again, even when a tar failed.
- **One volume**: pick the **Service**, then one of the named volumes it mounts, or **Other volume**
  and type its full name.

<Screenshot name="compose-volume-backup-add" alt="The Add a backup dialog on a Compose stack with Back up set to The whole stack, a Destination, a Cron expression and Stop the stack while it runs switched on" caption="The whole stack is the default: one schedule backs up every named volume." />

The other fields:

| Field | What it does |
|---|---|
| **Name** | Such as `Nightly uploads`. |
| **Destination**, **Prefix** | The bucket and the path the tarballs go under. |
| **Cron expression** | When it runs, such as `0 2 * * *` (every day at two in the morning). |
| **Keep the newest** | How many to keep; older ones are deleted after each successful run. Empty keeps all. |
| **Stop the stack while it runs** | Whole stack: stops every service once for the copy and starts them again afterwards. On by default when a service runs a `postgres`, `mysql`, `mariadb` or `mongo` image. |
| **Stop the service while the backup runs** | One volume: stops that service for the copy. |
| **Enabled** | Off keeps the backup and stops it firing. |

**Run now** runs it at once; the run history shows how each run went. While a backup that stopped
the stack is copying its volumes, **Remove containers** is refused (409) until it finishes.

<Screenshot name="compose-volume-backups" alt="The Volume backups tab of a Compose stack listing a whole-stack backup, with its schedule, Destination and how many it keeps, and the run history below" caption="A whole-stack backup shows The whole stack in its Volume column." />

<Callout type="note" title="Upgraded from before 0.3.13? Deploy the stack once first">
The volume pickers list what the stack's last successful Deployment recorded, and Deployments
record each service's named volumes from Cloudgate 0.3.13. Until a stack has deployed on 0.3.13 or
later, the tab says it has not deployed successfully yet (or that its volumes are recorded at its
next deploy) and **One volume** offers only **Other volume**. Redeploy it once to pick its volumes.
</Callout>

### How do I restore a stack's volumes?

Use **Restore** in the backup row's menu. For a whole-stack backup, the dialog lists the moments its
Destination holds: pick one, type the stack's name and press **Restore this moment**. It runs as one
restore, with each step shown: remove the containers (stop, on a Swarm stack), restore each volume,
then start the stack. If a volume fails, the restore stops there and the stack stays stopped.

For a one-volume backup, **Restore a volume** unpacks one tarball over that volume: press **Remove
containers** first and **Start** afterwards.

<Callout type="warn" title="A restore replaces the volume">
Restoring replaces the volume's contents, with no copy of what was there.
</Callout>

On a Swarm stack only the copy of a volume on the stack's Server is backed up.

## Advanced settings

### Keep the stack on its own network

**Network isolation** decides whether the stack shares Cloudgate's network with every other Service.
Turn on **Deploy onto its own network** and press **Save**: the next Deployment puts the routed
services on a network named after the stack, with Traefik connected so Domains still work. An
isolated stack cannot reach a managed database or another stack by name.

### Change how the stack is applied

**How it is applied** holds **Applied as** (**Docker Compose** or **Swarm stack**) and an optional
**Deploy command**, which replaces the generated one entirely. Write it from the subcommand, without
the word `docker`, for example
`compose -p <stack name> -f docker-compose.yml up -d --build --remove-orphans --quiet-pull`.

After switching the kind, deploy: the next deploy removes the old kind's containers and network
(not its volumes) and brings the stack up the new way. With your own deploy command, nothing is
removed for you.

### Repository settings

For a repository stack, **From the repository** holds the **Compose file** path, **Clone
submodules**, and **Watch paths**. Nothing reads watch paths yet, because no push deploys a stack.

### Delete a stack

**Delete this stack** on **Advanced** has the button **Delete** followed by the stack's name. The
dialog lists what goes: every container, the project directory on the machine, and the stack's
stored file, variables, Domains and Deployment history. Type the stack's name and press **Delete
stack**.

- Docker Compose: tick **Delete its volumes too** to remove its named volumes as well.
- Swarm stack: named volumes are always left behind; remove them on the Server if you want the disk.
- A stack never deployed leaves nothing behind.

If the machine cannot be reached, or containers are still there after the teardown, the stack is
kept and the dialog says why, with **Remove from Cloudgate anyway**. That deletes the record without
confirming the machine is clean, then lists what it could not confirm; **I have a copy of this**
closes the list, which is not stored anywhere.

<Callout type="warn" title="Deleting cannot be undone">
**Delete its volumes too** removes the stack's data with it, such as a database's data directory or
an upload folder.
</Callout>

## After a server reboot

From Cloudgate 0.3.9, a Compose stack on a Server comes back after the machine reboots: the
`cloudgate-boot-recover` unit starts the containers Docker could not start before the Swarm network
was up. A stack you stopped stays stopped. A Server added before 0.3.9 gets that unit from **Run
setup again** on its **Infrastructure** tab. See [Servers](/docs/guide/servers).

## Compose stacks in AWS and Google Cloud

In an Environment whose Deploy target is a Cloud account, each Compose stack runs on its own
**Stack VM** in that account and region, inside the Environment network. The Environment's next
[Plan](/docs/guide/project-config) makes the VM. The stack's Overview has a **Stack VM** card with
the **Machine type**, **Data disk** (snapshotted daily), monthly **Cost** and whether it is **Made**.

- Its Domains are rules on the Environment network's load balancer, with a certificate from the
  cloud. There is no generated host: type your own and add the DNS records Cloudgate shows at your DNS
  provider. Each service's **Port** is published on the Stack VM, open to the load balancer alone, and
  two services cannot share one.
- Only the Docker Compose kind runs there: a `type: stack` entry is refused.
- The **Containers** tab has no per-container actions; the stack's **Restart** restarts its
  containers. There is no **Volume backups** tab.
- Delete takes a final snapshot of the data disk unless its data is deleted too.

### Resize a Stack VM or grow its disk

A Stack VM changes only through its Environment's Plan. Pick a new **Size** (xsmall 0.25 CPU and
512 MB, doubling to 2xlarge 8 CPU and 16 GB) or a larger **Data disk (GB)** on the Stack VM card and
save, or change `size` in the Project config. The Plan shows a change line with the old and new
monthly price; a new size restarts the Stack VM, for example "analytics Stack VM: t3.small (2 vCPU,
2 GB) → t3.medium (2 vCPU, 4 GB), restarts the Stack VM". A disk grows in place with no restart, and the Apply grows its filesystem. A
disk only grows: a smaller size is refused. A stack the Project config describes takes its size from
its entry.

When Cloudgate's pinned Ubuntu image, Docker Engine or compose plugin moves on, the Plan offers a
**replace VM** line naming each pin's old and new value. Applied, it makes a new Stack VM, keeps the
data disk and its volumes, and deploys the stack onto it.

### Stop, start and restart a stack on a Stack VM

| Action | What it does |
|---|---|
| **Stop** | Stops the stack's containers, then stops the VM, so a stopped stack pays only for its disk. |
| **Start** | Starts the VM, waits until its tunnel answers, then starts the containers Stop stopped. |
| **Restart** | Restarts the stack's containers and never touches the VM. |

A Deployment of a stack whose Stack VM is stopped is refused ("start it first"), and so is any
action before the Environment's Plan has made the VM. A
[frozen Organization's](/docs/guide/organizations) Stack VMs keep running, and Stop is refused like
any other change.

<Callout type="limit" title="Cloud account permissions">
A Stack VM needs permissions that older Cloud account setups lack: AWS policy version 4
(self-hosted) or 5 (Hosted), and Google Cloud role version 7 (self-hosted) or 8 (Hosted). Until the
account is updated, a Plan that needs a Stack VM is refused, naming the missing actions and the fix.
See [Cloud accounts](/docs/guide/cloud-accounts).
</Callout>

## Describe a stack in the Project config

A stack whose file is in a repository can be written in the
[Project config](/docs/guide/project-config):

```yaml
services:
  analytics:
    kind: compose
    source:
      github: northwind/analytics
    file: deploy/docker-compose.yml
    type: docker-compose
```

`file` is optional. An entry without it names no file, and each deploy finds the first of
`compose.yaml`, `compose.yml`, `docker-compose.yaml` and `docker-compose.yml` in the repository's
root. A stack made before Cloudgate 0.3.13 that saved `./docker-compose.yml` keeps that file, and
its Plan shows no change.

The config names the file; it never holds a copy. A change to the file's contents reaches the stack
at its next Deployment, not as a Plan line. A stack whose file is written in Cloudgate stays
console-managed: the config lists it by name and kind, and a Plan never changes or destroys it.

## What you cannot do

<Callout type="limit" title="Limits of a Compose stack">
- Deploy a stack by pushing to its repository.
- Use previews, rollbacks or patches: those are for Applications.
- Reserve GPUs for a Compose stack. Its containers are not kept off a GPU Server's cards either.
- Run a Swarm stack in a Cloud account, or move a stack to another Server.
- Back up volumes from the Volume backups tab on a Stack VM; its data disk snapshots stand in.
- Change the generated Docker stack name.
</Callout>
