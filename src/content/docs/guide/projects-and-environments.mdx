The model is **Organization, Project, Environment, Service**. A Project such as `storefront` holds
Environments such as `production` and `staging`; each Environment holds Services such as `web`
and `pg-main`. A Project itself contains only its Environments, its Project variables, its
[Project config](/docs/guide/project-config) and its tags.

| Level | What it holds | Where in the console |
|---|---|---|
| Organization | Servers, members, tags, every Project | The rail |
| Project | Environments, Project variables, the Project config | **Projects** > a Project |
| Environment | Services, Environment variables, Domains, a Deploy target, a Config branch | A Project > **Environments** > an Environment |
| Service | An Application, a database, a Compose stack, a bucket or an AI model | An Environment > **Services** |

## Find a Project in the Projects list

Open **Projects** in the rail. The list, "Everything this Organization deploys, grouped by what
ships together", has one row per Project, sorted by name:

| Column | What it shows |
|---|---|
| **Project** | The name, linking to the Project, with its description under it |
| **Environments** | How many Environments it has that you can see |
| **Tags** | Up to three tags; more show as `+2`, with the rest in its tooltip. "No tags" when it has none |
| **Created** | When it was made |
| Row menu | **Rename**, **Tags** and **Delete** (see below) |

Above the table, **Search Projects** matches the name and the description, and **Tags** filters
by tag (see [Group Projects with tags](#group-projects-with-tags)). The line above the rows reads
"3 Projects here", or "Showing 1 of 3" while a search or filter is on. When nothing matches, the
list says **No Project matches**: clear the search and the tag filter.

<Screenshot name="projects-list" alt="The Projects list of the Northwind Labs organization, with the ai-lab, analytics and storefront Projects, their Environments count, tags and creation date" caption="Each row is a Project; open one to see its Environments." />

<Callout type="limit" title="You see only what you are granted">
Owners and admins see every Project. Every other member sees only the Projects they have been
granted, and the **Environments** count counts only the Environments granted to them. Ask an
owner or admin to grant more under [Members and roles](/docs/guide/members-and-roles).
</Callout>

While the Organization has no Project, the list shows **Make your first Project** and a card,
**The hierarchy**, that explains Organization, Project, Environment and Services.

## Create a Project

<Steps>
<Step title="Open the dialog">
On **Projects**, press **New Project** (or **New Project** in the empty list).
</Step>
<Step title="Name it">
Fill in the dialog and press **Create Project**.

| Field | What it does | Notes |
|---|---|---|
| **Name** | How the Project is found, for example `storefront` | Required. Unique in the Organization, whatever the letter case |
| **Description** | A short note shown under the name in lists | Optional |
</Step>
<Step title="Add its first Environment">
The new Project opens on its **Environments** tab, with the note "Add an Environment to it to
start deploying". Continue with [Add an Environment](#add-an-environment).
</Step>
</Steps>

If the name is taken, the dialog says "A Project with this name already exists in your
organization" under **Name**. If **New Project** is greyed out, your role cannot create a Project:
its tooltip says so, and an owner or admin can make one or change your role.

## Rename a Project or change its description

Use the row menu on **Projects** > **Rename**, or the Project's **Settings** tab > **Project**
card. Change **Name** or **Description** and press **Save changes**. Renaming changes how the
Project is found and renames nothing deployed under it.

## Group Projects with tags

A tag is an Organization-wide label, such as `billing` or `client-acme`, that you put on Projects
to filter the list by it. Tags are for Projects only; they change nothing that runs.

### Create, rename and delete tags

Press **Manage tags** on **Projects**. In the dialog:

- **New tag**: type a name and press **Add tag**. Names are unique in the Organization, whatever
  the letter case.
- **Rename** on a row: edit the name and press **Save** (or Enter); **Cancel** or Esc keeps it.
- **Delete** on a row: confirm "Delete billing? It comes off every Project that carries it." with
  **Delete**. The tag is taken off every Project at once.

Press **Done** to close.

<Screenshot name="projects-manage-tags" alt="The Manage tags dialog listing the tags billing, client-acme and internal, each with Rename and Delete" caption="Tags are shared by the whole Organization." />

### Put tags on a Project

On **Projects**, open a row's menu and choose **Tags**. The dialog **Tags on storefront** lists
every tag with a checkbox: tick one to put it on the Project, untick it to take it off. Each tick
is saved at once. With no tags yet, it points you to **Manage tags**.

### Filter the list by tag

Press **Tags** beside the search. Tick one or more tags: the list keeps the Projects that carry
**any** of them, and the button shows how many are ticked. **Clear filter** unticks them all. A
tag deleted meanwhile drops out of the filter by itself.

<Screenshot name="projects-tag-filter" alt="The Tags filter open on the Projects list with billing ticked, and only the storefront Project listed, Showing 1 of 3" caption="A Project matches when it carries any ticked tag." />

| Action | Who |
|---|---|
| See tags and filter by them | Every member |
| Create, rename or delete a tag | Owner, admin, or a custom role with those tag permissions |
| Put a tag on a Project or take it off | Whoever may change the Project (owner, admin, or a custom role with Project update) |

## What is on a Project's page?

A Project has three tabs in the rail, with **Back to Projects** above them:

| Tab | What it is for |
|---|---|
| **Environments** | The Project's Environments, and **New Environment** |
| **Config** | The [Project config](/docs/guide/project-config) and each Environment's Plan |
| **Settings** | Name and description, **Project variables**, and **Delete this Project** |

The **Project** card beside the Environments and Settings tabs lists its **Name**,
**Environments**, the number of **Project variables** and, once an Environment runs an
[AI model](/docs/guide/ai-models), **Token spend, 30 days** in total and per Environment.

### The Environments tab

Each row shows the **Environment** (name and description), how many **Variables** are set on it,
and when it was **Created**. Its menu has **Rename** and **Delete**. With none yet, it shows **Make
your first Environment**: "Most Projects start with one called production."

<Screenshot name="project-overview" alt="The Environments tab of the storefront Project listing production and staging, with the Project card beside them" caption="Open an Environment to see its Services." />

### Project variables

The **Settings** tab holds **Project variables**: "Set once here, for anything below to
reference." Nothing receives them automatically. A Service in any Environment of the Project
uses one by naming it as `${{project.KEY}}`. Press **Add variables** (or **Edit**), write one
`KEY=value` per line and press **Save variables**. Values whose names look secret are hidden until
you press **Show values**. See [Environment variables](/docs/guide/environment-variables) for the
whole picture.

<Screenshot name="project-variables" alt="The Project variables card on the storefront Project's Settings tab, with LOG_LEVEL and NODE_ENV shown and SENTRY_DSN and STRIPE_PUBLISHABLE_KEY masked" caption="Project variables reach a Service only where it names them." />

## Add an Environment

An Environment is one copy of what the Project deploys, with its own variables: `production`,
`staging`, a person's name, or a short-lived copy such as `pr-482`.

<Steps>
<Step title="Open the dialog">
On the Project's **Environments** tab, press **New Environment**.
</Step>
<Step title="Fill it in">

| Field | What it does | Notes |
|---|---|---|
| **Name** | "What this copy is for — production, staging, a person's name." | Required. Unique in the Project, whatever the letter case |
| **Description** | A short note shown under the name in lists | Optional |
| **Deploy target** | Where a Service created in this Environment will run | See below. You can change it later |
| **AWS region** or **Google Cloud region** | The region in the chosen Cloud account | Shown only for a Cloud account |

<Screenshot name="environment-new-dialog" alt="The New Environment dialog for storefront with Name qa and the Deploy target list open, showing This Cloudgate host, nyc-edge and fra-1" caption="On a self-hosted instance the list also offers This Cloudgate host." />
</Step>
<Step title="Create it">
Press **Create Environment**. It opens on its **Services** tab: "Add an Application, a database or
a Compose stack to it."
</Step>
</Steps>

### What the Deploy target list offers

- **A Server** of yours, by name and address. One whose setup has not finished is listed with the
  reason and cannot be picked. Build Servers are never listed: they run no Service.
- **This Cloudgate host**, the machine Cloudgate itself runs on: self-hosted only. A self-hosted
  dialog opens on your first ready Server. Picking the Cloudgate host shows a warning: if that
  machine is lost, the Service and all of Cloudgate's records go with it, so add a Server or use the
  Hosted instance to keep them apart.
- **A Cloud account** (AWS or Google Cloud), shown on the Hosted instance to members who may read
  Cloud accounts. Pick it, then its region. Saving checks the account in that region and creates
  nothing. The region hint says what Cloudgate can create there: on AWS, web Services, PostgreSQL,
  Redis, buckets and static sites (not yet workers, cron, private web Services or MySQL); on Google
  Cloud, web Services, PostgreSQL and Redis (not yet buckets or static sites). A self-hosted
  instance picks a Cloud account later, on the Environment's **Settings** tab.

A self-hosted Organization with no Server of its own is not asked at all: the Environment deploys to
the Cloudgate host.

<Callout type="limit" title="Hosted: a Server or a Cloud account first">
On the Hosted instance the Cloudgate host is never a Deploy target. With no Server and no Cloud
account, the dialog says "An Environment needs a Server or a Cloud account to deploy to, and this
Organization has neither yet", with **Add a Server** and **Connect a Cloud account**, and
**Create Environment** stays off. Choosing a Cloud account also counts as one Cloud Environment on
your [Plan](/pricing); when the Plan's count is full, the choice is refused and nothing is saved.
</Callout>

## What is on an Environment's page?

An Environment has five tabs, with **Back to** its Project above them:

| Tab | What it shows |
|---|---|
| **Services** | Everything deployed here, the add buttons, pending template setups |
| **Deployments** | "Every build and release into this Environment, newest first" |
| **Variables** | The Environment's variables, and what is available from the Project |
| **Domains** | Every Domain answered by something here, and which Service answers it |
| **Settings** | Name and description, Deploy target, Config branch, Delete |

The **Environment** card beside most tabs lists its **Name**, its **Project** (a link), how many
**Variables** it has, **Token spend, 30 days** when it runs an AI model, and when it was
**Created**.

### The Services tab

The list holds every Application, database, Compose stack, bucket and AI model in the Environment:

| Column | What it shows |
|---|---|
| **Name** | The Service, linking to it, with its internal name under it |
| **Type** | Application, PostgreSQL, MySQL, MariaDB, MongoDB, Redis, libSQL, Compose stack or Bucket, and when it was created |
| **Status** | Its current status |
| **Health** | `up`, `down`, `Incident open`, `not probed yet` or `not checked`, from its [health checks](/docs/guide/monitoring) |
| **Spend** | Token spend over 30 days, shown only when the Environment runs an AI model |
| **Open** | Opens the Service |

<Screenshot name="environment-services" alt="The Services tab of storefront production, listing api, cache, jobs, media, nightly-report, orders-db and web with their type, status and health" caption="The Services tab lists everything the Environment runs." />

The buttons above the list are where Services are added:

| Button | What it opens |
|---|---|
| **Add an Application** | The Application dialog: see [Applications](/docs/guide/applications) and [workers and cron](/docs/guide/workers-and-cron) |
| **Add a database** | The database dialog: see [Databases](/docs/guide/databases) |
| **Add a Compose stack** | The Compose dialog: see [Compose stacks](/docs/guide/compose-stacks) |
| **Draft one with AI** | Drafts a Compose stack from a description, with your AI provider: see [Compose stacks](/docs/guide/compose-stacks) |
| **Set up a template** | The [Templates](/docs/guide/templates) list, with this Project and Environment already chosen |
| **Add an AI model** | The AI model dialog: see [AI models](/docs/guide/ai-models). Shown only to roles that may add Services |

There is no button for a bucket: a [bucket](/docs/guide/buckets) is created by the Project config.
Adding a Service needs Service create, which owners and admins have and the member role does not;
for other roles the buttons are off, with the reason in their tooltip.

<Callout type="note" title="A Service in a cloud Environment">
When the Deploy target is a Cloud account, only the [Project config](/docs/guide/project-config)
creates cloud Services. A Service added with these buttons runs on a Server, or on the Cloudgate
host chosen on purpose, and its dialog asks which.
</Callout>

When the list is empty it says **Nothing is deployed here yet**. A member who has been granted no
Service here sees **You have not been given access to any Service here** instead: an owner or
admin grants one under **Members**, **Manage access**.

### Pending setups

A [Template](/docs/guide/templates) set up into this Environment waits as a **Pending setup** until
an Apply of the Plan creates its parts. The **Pending setups** card lists each one: its setup name
and Template, the Config names it **Creates**, how many values are ready, and when it
**Expires**. **Review the plan** opens the Environment's Plan on the Config tab.

**Cancel setup** asks "Cancel the ghost setup?" and, on **Cancel setup**, drops it and every value
it made; generated values cannot be made again. **Keep it** leaves it. A setup with no Apply after
30 days is dropped by itself, and the card says so with its name and what it would have created.

<Screenshot name="environment-pending-setups" alt="The Pending setups card in storefront staging, with the blog setup of the Ghost template that creates blog-app, 8 values ready, expiring Dec 27" caption="Apply the Plan to create the setup's Services, or cancel it." />

### The Deployments tab

The Deployments of every Service here, newest first, with the **Service** each belongs to (and,
for a scheduled run or a backup, which one). Deployments run on a Service, not on an Environment:
press **Open** to go to that Service's Deployments to build again or read the output. See
[Deployments](/docs/guide/deployments).

### The Variables tab

"Variables any service in this Environment can reference by name." Edit them on the **Variables**
card; a Service uses one as `${{environment.KEY}}`. **Available from the Project** lists the
Project variables, read-only. **How variables reach a service** sums it up: by reference, not by
inheritance. Details in [Environment variables](/docs/guide/environment-variables).

### The Domains tab

Every host that points into this Environment, with the **Service** that answers it, its
**Certificate** and **Open**, which goes to that Service's Domains tab. A Domain is added on the
Service itself. For an Application the change takes effect within a second; for a Compose stack,
at its next Deployment. Managed databases have no Domains. See
[Domains and HTTPS](/docs/guide/domains).

## Change an Environment's name or Config branch

On the Environment's **Settings** tab:

- **Environment** card: change **Name** or **Description** and press **Save changes**. Renaming
  renames nothing deployed in it. The Project's **Environments** tab row menu > **Rename** does
  the same.
- **Config branch** card: the branch this Environment reads the Project config from when the
  config is kept in a repository. Leave **Branch** empty for the repository's default branch. A
  Service the Plan creates from that same repository builds from this branch too. Press **Save
  Config branch**; the next Plan reads the new branch. Branch names have no spaces.

## Change where new Services are created

On **Settings** > **Deploy target**, pick a Server, the Cloudgate host (self-hosted) or a Cloud
account and region, then press **Save Deploy target**. The toast says where new Services will be
created and that nothing already running moved. A region check can come back with a warning, such
as a quota nearly reached, shown under the card.

<Screenshot name="environment-deploy-target" alt="The Deploy target card on storefront staging's Settings tab with nyc-edge chosen and Save Deploy target" caption="Changing it moves nothing that already runs." />

<Callout type="limit" title="Nothing moves a Service">
A Service's place, a Server or a Cloud account, is fixed when it is created. To run it somewhere
else, create a new Service there and delete the old one. If the saved target is a Server or Cloud
account you cannot list, the card shows "A Server you cannot list" or "A Cloud account you cannot
list".
</Callout>

## What is the Environment network?

An Environment with Services in a Cloud account gets one **Environment network** per account and
region, shared by its Services there. Its card on the Services tab shows:

| Row | What it means |
|---|---|
| **Where** | The Cloud account and region |
| **Status** | being made, ready, not made, deleting or delete incomplete |
| **Load balancer** (AWS) or **Fixed IP** (Google Cloud) | Its address, or "Not made yet" |
| **Idle cost** | What it costs with nothing in it |
| **Services in it** | How many Services use it; "None — it still bills" when empty |

**Open its log** shows its latest Cloud run. **What it made** lists the cloud resources from its
Infrastructure state, never a setting's value. If Cloudgate cannot read that state, a banner says
so: **Rebuild from the cloud** discards the state, after you type the Environment's name, and makes
a Plan that takes back what Cloudgate's tags (AWS) or names (Google Cloud) find. Nothing changes in
the cloud until you apply that Plan. Rebuilding needs Environment update. More in
[Cloud accounts](/docs/guide/cloud-accounts).

## Delete an Environment

<Callout type="warn" title="This cannot be undone">
Deleting an Environment deletes everything deployed in it: its Applications, databases and Compose
stacks, their volumes, and the variables set on it. The Project keeps its other Environments.
</Callout>

<Steps>
<Step title="Start the Delete">
On the Environment's **Settings** tab, press **Delete** beside **Delete this Environment**, or use
the row menu on the Project's **Environments** tab.
</Step>
<Step title="Confirm by name">
Read what will go, type the Environment's name in **Type staging to confirm**, and press **Delete
Environment**. A wrong name says "That does not match the Environment's name."
<Screenshot name="environment-delete-dialog" alt="The Delete staging dialog naming what is deleted, including the 4 variables set on it, with staging typed to confirm and Delete Environment" caption="The dialog names what goes before you confirm." />
</Step>
</Steps>

A bucket that holds files is kept, its volume with it, and named in the toast when the Delete ends;
an empty one is removed. Deleting an Environment never deletes a bucket's files.

### Deleting an Environment in a Cloud account

In a Cloud account, its cloud Services are deleted first, then its Environment network, each in a
Cloud run with its own log; on Google Cloud every Domain is taken off the network before that. The
Environment shows a **Deleting staging** card until the account is checked and nothing is left.
Cloudgate never writes DNS, so the toast lists any DNS records to remove at your DNS provider.

If anything is left, the card turns into **Delete incomplete**, listing each resource (its type,
id, region and Cloudgate tag or label) that may still bill:

- **Retry** deletes again from what its Infrastructure state still holds.
- **Forget** asks "Forget staging?" and, on **Forget**, drops the Environment from Cloudgate. What
  it left is kept only in the [audit log](/docs/guide/audit-log) and may still bill you until you
  remove it in the cloud. **Keep it** cancels.

## Delete a Project

<Callout type="warn" title="This cannot be undone">
Deleting a Project deletes every Environment under it, everything deployed in them, and their
variables. Its tags come off it.
</Callout>

On the Project's **Settings** tab, press **Delete** beside **Delete this Project** (or use the row
menu on **Projects**). The dialog names its Environments, for example "Deleting storefront deletes
its 2 Environments — production, staging — and everything deployed in them". Type the Project's
name and press **Delete Project**. Buckets that hold files are kept and named, as for an
Environment.

- Cloudgate checks every Service first. If your role may not delete one of them, or a Service's
  containers cannot be confirmed gone, the whole Delete is refused with the reason in the dialog
  and nothing is removed.
- Environments in a Cloud account are deleted first, as above; the Project goes once they all are.
  If one ends as **Delete incomplete**, the Project stays: deal with that Environment, then delete
  the Project again.

## Who can do what

| Action | Who |
|---|---|
| Create, rename or delete a Project; edit Project variables; put tags on it | Owner, admin, or a custom role that allows it |
| Create or delete an Environment | Owner, admin, or a custom role that allows it |
| Rename an Environment, edit its variables, Deploy target and Config branch | Any member it is granted to (the member role includes Environment update) |
| Add a Service to an Environment | Owner, admin, or a custom role with Service create |
| Cancel a pending setup | Any member with Environment update |
| Create, rename or delete tags | Owner, admin, or a custom role that allows it |

A control your role cannot use stays visible but off, and its tooltip, or the line under it, says
"Your role in this Organization cannot ..." with who to ask. Custom roles are a paid feature; see
[Members and roles](/docs/guide/members-and-roles).

## What you cannot do

- Make Services inherit variables: they reference them by name.
- Rename something deployed by renaming its Project or Environment.
- Move a running Service by changing the Deploy target.
- Use the Cloudgate host as a Deploy target on the Hosted instance.
- Create a bucket, or a cloud Service, with a button: the Project config creates them.
- Clone or promote an Environment: the console has no such action. Use the
  [Project config](/docs/guide/project-config) so each Environment's Plan makes the same Services.
- Remove a Project variable that a Service references without failing that Service's next
  Deployment.
