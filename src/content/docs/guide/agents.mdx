An Agent has its own role, its own grant to the Projects, Environments and Services it may reach,
and its own **agent keys**. It acts only through the MCP endpoint, which is your console's address
plus `/mcp`, and every call it makes, allowed or refused, is a row in the
[audit log](/docs/guide/audit-log). Agents are included on every plan, Hosted and self-hosted.

## What you can do with Agents

- Create Agents with the **Reader**, **Operator** or **Caller** role.
- Grant each one only the Projects, Environments and Services it needs.
- Let a Reader or Operator read the Runtime logs of what it is granted, with **Can read runtime
  logs**.
- Issue, rotate, revoke and remove its agent keys, each with an expiry.
- Copy ready-made configuration for Claude Code, VS Code, Cursor, Codex CLI and other MCP clients.
- See when each Agent was last used, which client last connected, and how often it hit a rate limit.
- Suspend an Agent at once, and resume it later.

## Who can manage Agents?

Any member of the Organization can open **Settings** > **Agents** and read its Agents. Only an
Owner or an Admin can create, change, suspend or delete one, add and revoke its keys, or turn its
**Can read runtime logs** switch on or off. Everyone
else sees those buttons off, with the reason. The link to an Agent's calls in the audit log shows
only to a role that can read the audit log; others see "Its calls are in the audit log, which your
role cannot read."

## Which role should an Agent have?

Give an Agent the least it needs: **Reader** to look, **Operator** to deploy, **Caller** only to
call AI models.

| Role | What it can do |
|---|---|
| **Reader** (default) | Reads what it is granted: Services, Environments, Deployments, Deployment logs and Domains. Cannot deploy, start, stop or change anything. |
| **Operator** | Everything a Reader can, and deploys, starts, stops and cancels Deployments of what it is granted, including Compose stacks. Cannot change settings, variables or access. |
| **Caller** | Calls the AI models it is granted through their endpoint, and nothing else. Gets no tools over MCP. |

A Reader and an Operator also read the container metrics of the Services they are granted, and the
Runtime logs of those Services when their **Can read runtime logs** switch is on. An Agent can never
hold the Owner, Admin or Member role. The tools each role may call are listed in
[MCP tools](/docs/mcp/tools) and [Guard rails](/docs/mcp/guard-rails).

## Create an Agent

<Steps>
<Step title="Open Agents">
Open **Settings** > **Agents** and press **Create an Agent**. With no Agents yet, the page shows
**No Agents yet** and the same button.
</Step>
<Step title="Name it">
Give it a **Name** of up to 64 characters that says what it is for, such as `deploy-bot` or
`staging reader`. It is how the audit log names it.
</Step>
<Step title="Pick a role">
Under **Role**, pick **Reader**, **Operator** or **Caller**. Reader is selected by default.
</Step>
<Step title="Grant access">
Under **Access**, tick what it may reach, for example the `storefront` Project's `staging`
Environment. Access starts empty. An Agent reaches a Service through its Project and its
Environment, so granting a Service grants the two above it. You can save it with nothing granted and
grant it later; until then its status reads **reaches nothing yet**.

The dialog warns: "This Agent can always read the Deployment logs of what you grant, and their
Runtime logs only with Can read runtime logs on. Cloudgate masks the secrets it stores, not what a
build or a running Service prints."
</Step>
<Step title="Decide on runtime logs">
Under the access tree, **Can read runtime logs** is off: "What its Services print as they run, which
can hold anything their users sent them. Off unless you turn it on." Turn it on only if the Agent
should read what the Services you granted print while they run, for example to find why one keeps
crashing. The switch is not offered for a Caller.
<Screenshot name="agent-create" alt="The Create an Agent dialog with the name deploy-bot, the Operator role selected, the storefront Project and its staging Environment ticked, and the Can read runtime logs switch off below the access tree" caption="Grant the smallest scope that does the job; Can read runtime logs stays off unless you turn it on." />
</Step>
<Step title="Choose when its first key expires">
Under **First key expires**, choose **In 30 days**, **In 90 days** (the default) or **In a year**.
Every agent key expires. Press **Create Agent**.
</Step>
<Step title="Copy the key">
The dialog turns into **deploy-bot's first key**: "This is the only time it is readable." Copy the
key into your MCP client's secret storage. A Reader or Operator key is sent only to this console's
MCP endpoint, as a bearer token, and is refused everywhere else; a Caller key is sent to an AI
model's endpoint and reaches no MCP tool. The same dialog holds the client configuration. Press
**I have copied it**.
<Screenshot name="agent-key-reveal" alt="The first key of deploy-bot shown once with a Copy button, followed by the client configuration tabs" caption="The key is never shown again: Cloudgate keeps only a hash of it." />
</Step>
</Steps>

An AI model's **Model** tab also offers **Create a caller Agent**: the same dialog, preset to the
Caller role and that model. See [AI models](/docs/guide/ai-models).

## Connect an MCP client

On the Agent's row, press **Connect**. The dialog **Connect deploy-bot** reminds you that a key
cannot be recovered, then gives the configuration for each client. None of the snippets holds the
key, so they are safe to commit. Each sends the key as `Authorization: Bearer <agent key>` to your
console's address plus `/mcp`.

| Tab | File | Where the key comes from |
|---|---|---|
| **Claude Code** | `.mcp.json` | The `CLOUDGATE_AGENT_KEY` environment variable. Claude Code asks once before it uses a project's `.mcp.json`. |
| **VS Code** | `.vscode/mcp.json` | VS Code asks for it the first time it starts the server and keeps it in its own secret storage. |
| **Cursor** | `~/.cursor/mcp.json` | The `CLOUDGATE_AGENT_KEY` environment variable. |
| **Codex CLI** | `~/.codex/config.toml` | The `CLOUDGATE_AGENT_KEY` environment variable, sent as the bearer token. |
| **Any other client** | Your client's own | Replace `<agent key>` with the key, or with your client's way of reading `CLOUDGATE_AGENT_KEY`. |

Press **Copy** on the tab, paste it into the file, and press **Done**. For example, Claude Code's
snippet:

```json
{
  "mcpServers": {
    "cloudgate": {
      "type": "http",
      "url": "https://console.northwind.example/mcp",
      "headers": { "Authorization": "Bearer ${CLOUDGATE_AGENT_KEY}" }
    }
  }
}
```

## Read an Agent's row

<Screenshot name="settings-agents" alt="Settings, Agents for Northwind Labs, with deploy-assistant (Operator) and incident-triage (Reader), each with its access, keys and when a client last connected" caption="Each Agent shows its role, what it can reach, its keys and when a client last connected." />

Each Agent's row shows:

| Part | What it says |
|---|---|
| Role and status | **active**, **reaches nothing yet** (no grant), **no valid key** (every key expired or none left) or **suspended**. |
| Access | A summary such as "1 Project · 2 Environments"; press it to list each grant. A grant to something deleted, or outside its granted Project, is named as unreachable. |
| **Keys** | How many, and when the next expires. Each key shows its first characters, **Created**, **Last used** or **Never used**, and **Expires** or **Expired**. A key due within 14 days is marked. |
| **Last used** | The newest use of any of its keys. |
| **Last connected** | The client that last connected, with its version and MCP revision, or "No client has connected yet". |
| **Can read runtime logs** | **On** or **Off**, with its switch and "Cloudgate masks the secrets it stores, not what an app prints." Not shown for a Caller. |
| **Created** | When, and by whom. |
| Rate limits | "Rate-limited n times in the last hour", linking to its refused calls, when it happened. |
| Audit log | **Every call it made, in the audit log**, filtered to this Agent. |

## Let an Agent read runtime logs

**Can read runtime logs** lets a Reader or Operator Agent read the Runtime log of each Application
and Compose stack it is granted: the last lines the Service printed while running, from every copy,
through the MCP tool `read_runtime_log`. It is off unless you turn it on, and it never widens the
grant: an Agent reads only the Runtime logs of Services it can already reach.

- Turn it on when you create the Agent, or later with the switch on its row. Only an Owner or an
  Admin can change it; for anyone else the switch is disabled and says why.
- A change applies to the Agent's next call. The console confirms it, for example "deploy-bot can
  read runtime logs.", and every change, including one at creation, is in the
  [audit log](/docs/guide/audit-log).
- With it off, the tool is refused with a message naming the switch, so the agent can tell you what
  to turn on.
- A Caller never holds it. Changing an Agent to **Caller** turns it off, and **Change role** says so
  before you confirm: "A Caller cannot read runtime logs, so this turns that off."
<Screenshot name="agent-runtime-logs" alt="An Agent's row in Settings, Agents with the Can read runtime logs switch on, and the note that Cloudgate masks the secrets it stores, not what an app prints" caption="The switch shows what Cloudgate holds; a refused change leaves it where it was." />

<Callout type="warn" title="The mask cannot hide what an app prints">
A Runtime log is whatever your Services print, which can include your users' emails, request bodies
and session tokens that Cloudgate never stored. The mask replaces only the secrets Cloudgate stores.
Turn the switch on only for an Agent whose model host you would trust with that output. See
[what the mask cannot hide](/docs/mcp/guard-rails#what-does-the-secret-mask-hide).
</Callout>

## Rotate an Agent's keys

An Agent can hold several keys, each with its own expiry, so you can rotate without downtime:

1. Press **Add key** on its row. In **Add a key to deploy-bot**, choose **Expires** (**In 30 days**,
   **In 90 days** or **In a year**) and press **Add key**. Its other keys keep working.
2. Copy the new key from **deploy-bot's new key** and press **I have copied it**.
3. Switch the client to the new key.
4. Press **Revoke** on the old key, then **Revoke key**. Whatever still uses it is refused on its next
   call. If it was the Agent's last valid key, the dialog warns that the Agent stops working until you
   add one.

An expired key shows **Remove** in place of **Revoke**; **Remove key** clears it from the list. Revoking
and removing cannot be undone.

## Suspend, resume, change or delete an Agent

| Button | What happens |
|---|---|
| **Suspend** | Asks **Suspend deploy-bot?** Press **Suspend Agent**: its next call through the MCP endpoint is refused, and every one after. Keys, role and access stay; anything it already started keeps running. **Keep it running** cancels. |
| **Resume** | Lets it call again at once, with no new key and no change in its client. |
| **Change role** | Pick another role and press **Change role**. It takes effect on its next call; keys and access stay. A move to Caller turns **Can read runtime logs** off. |
| **Manage access** | Tick or untick Projects, Environments and Services and press **Save access**. It takes effect on its next call. |
| **Delete** | Asks **Delete deploy-bot?** Press **Delete Agent**: the Agent, its access and all its keys go, and its keys stop on the next call. Anything it deployed stays, and its audit trail stays. **Keep it** cancels. |

<Callout type="warn" title="Deleting an Agent cannot be undone">
Every client using its keys stops working at once, and a new Agent needs a new key in its client.
To stop it for now, use **Suspend** instead.
</Callout>

## What you cannot do

<Callout type="limit" title="Guard rails">
- Every agent key expires: there is no "never".
- An Agent can never be an Owner, an Admin or a Member.
- An Agent asks for a Plan but never applies or dismisses one, and reads health but never
  configures checks or thresholds.
- An Agent reads a granted Service's container metrics, never a Server's own metrics.
- An Agent reads a Runtime log only with **Can read runtime logs** on, and a Caller never can.
- Rate limits: 120 reads and 10 writes a minute per Agent, shared across its keys.
- An agent key works only at the MCP endpoint and the Gateway, never on the REST API or for
  sign-in. The MCP endpoint refuses personal keys.
- There is no approval step: an Agent's allowed call runs at once.
- Cloudgate does not give an Agent access to your git repository; you do that outside Cloudgate.
</Callout>
