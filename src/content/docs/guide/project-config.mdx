The Project config describes each Service by its Config name: its kind, size, source, build,
port and variable names. It is kept either in Cloudgate, edited on the Project's **Config** tab,
or in your repository as `cloudgate.yaml` (or `cloudgate.yml`) at the root, unless you name another
path.

A **Plan** is one Environment's list of what applying the config would create, change and
destroy. Each Environment has at most one open Plan.

## What you can do

- Describe Applications (`web`, `web-private`, `worker`, `cron`, `static`), PostgreSQL, MySQL,
  Redis, buckets and Compose stacks in one file.
- Link variables to another Service's Outputs, such as a database's URL.
- Keep the file in Cloudgate or in your repository, and move it either way.
- Edit a Cloudgate-kept config from a folder on your computer with the CLI, and build apps from
  that folder's subfolders.
- Review each Environment's Plan, including drift in a cloud, and Apply or dismiss it.

## An example cloudgate.yaml

A shop with a web app, a background worker, a nightly report, PostgreSQL, Redis and a bucket for
uploads:

```yaml
# yaml-language-server: $schema=https://cloudgate.octabyte.app/backend/schema/project-config/v1.json
version: 1

services:
  web:
    kind: web
    description: The storefront
    size: small
    source:
      github: northwind-labs/storefront
      path: apps/web
    build:
      type: nixpacks
    port: 3000
    env:
      - SESSION_SECRET
      - DATABASE_URL: pg-main.url
      - REDIS_URL: cache.url
      - S3_BUCKET: uploads.name
      - S3_ENDPOINT: uploads.endpoint
      - AWS_ACCESS_KEY_ID: uploads.access_key_id
      - AWS_SECRET_ACCESS_KEY: uploads.secret_access_key
    build_args: [NEXT_PUBLIC_SITE_URL]

  jobs:
    kind: worker
    size: xsmall
    source:
      github: northwind-labs/storefront
      path: apps/jobs
    command: node
    args: [dist/worker.js]
    env:
      - DATABASE_URL: pg-main.url
      - REDIS_URL: cache.url

  nightly-report:
    kind: cron
    source:
      github: northwind-labs/storefront
      path: apps/jobs
    command: node dist/report.js
    schedule: "0 3 * * *"
    timezone: Europe/Berlin
    timeout: 30m
    env:
      - DATABASE_URL: pg-main.url

  pg-main:
    kind: postgres
    size: small
    version: "18"
    database: storefront
    user: storefront

  cache:
    kind: redis
    version: "8"

  uploads:
    kind: bucket
```

What the fields mean:

- **Config names** (`web`, `pg-main`) are lower-case letters, digits and hyphens, starting with a
  letter, at most 63 characters. A Plan matches entries by Config name, so a renamed entry reads as
  a new Service to create and the old one to destroy.
- `env` lists **names only**. `SESSION_SECRET` is set in the console. `DATABASE_URL: pg-main.url`
  is a [wired variable](/docs/guide/environment-variables): Cloudgate fills it from `pg-main`'s
  `url` Output at each Deployment and never saves it.
- `size` is `xsmall` to `2xlarge`, or `{ cpu: 1, memory: 2 GB }`. See
  [Applications](/docs/guide/applications) for the table.
- A database `version` is its image tag and must be quoted: `"18"` runs `postgres:18`.
- `source` takes `github`, `gitlab`, `gitea` or `bitbucket` with `owner/repo`, a `git` URL (no
  credentials in it), an `image`, or a `folder`: a subfolder of a
  [Project folder](#edit-the-config-from-a-project-folder), such as `{ folder: apps/web }`. A
  `web`, `worker`, `static` or `cron` can take a `folder`; a `web-private` cannot, and a `folder` is
  never combined with another source key.
- `build.type` is `nixpacks`, `railpack`, `dockerfile`, `heroku_buildpacks` or
  `paketo_buildpacks`.
- `kind: compose` names a compose file in a repository (`source`, `file`, `type`). The file's
  contents stay in the repository. `file` is optional: left out, each deploy finds the first of
  `compose.yaml`, `compose.yml`, `docker-compose.yaml` and `docker-compose.yml`. See
  [Compose stacks](/docs/guide/compose-stacks#describe-a-stack-in-the-project-config).

Kinds the config cannot describe yet, such as MongoDB, MariaDB and libSQL, appear as
`kind: mongo` with `managed: console`. A Plan never changes or destroys a console-managed entry.

<Callout type="tip" title="Validation in your editor">
The first line points your editor at the published JSON Schema, so it completes field names and
flags mistakes as you type. On a self-hosted instance, use your console's address in its place.
</Callout>

## Edit a config kept in Cloudgate

<Steps>
<Step title="Open the Config tab">
Open the Project, for example `storefront`, and its **Config** tab: "What this Project runs, as one
YAML file, and what applying it would change in each Environment." The **Project config** card says
"Kept in Cloudgate", with one Plan card per Environment below it.
<Screenshot name="project-config" alt="The Config tab of the storefront Project with the cloudgate.yaml text and the production and staging plan cards below, each saying Nothing to change" caption="The text above, one plan card per Environment below." />
</Step>
<Step title="Edit and plan">
Change the text and press **Save and plan**. Cloudgate plans each Environment below and says
"Planned in each Environment below. Nothing is applied, and the text is stored when you apply a plan
of it." When no Environment has anything to change, it says "Saved" and stores the text as it is.
A refused config shows the reason above the editor, naming the field.
</Step>
<Step title="Review the Plan">
Each Environment's card lists what applying would do, in sections such as **Creates**,
**Changes**, **Major upgrades** and **Destroys** (see [Read a Plan](#read-a-plan)).
<Screenshot name="plan-card" alt="The plan card for storefront production saying Nothing to change, with a note that the media bucket is missing from the config and the lines to paste" caption="Each card says what applying would change, or that nothing would." />
</Step>
<Step title="Apply">
Press **Apply** on the card of the Environment you want to change. Or press **Dismiss** to drop the
Plan.
</Step>
</Steps>

The card's other buttons:

| Button | What it does |
|---|---|
| **Copy** | Copies the text, for example to commit it beside your code |
| **Wrap lines** | The switch under the editor. Long lines scroll sideways by default, so indentation reads as written; on, they wrap. Your browser remembers it for every editor |
| **Expand** | Opens the editor filling the window, with **Discard edits** and **Save and plan** in its top bar and a status line saying whether the YAML is valid. **Back to page** or Esc returns with your edit kept |
| **Move to a repository** | Keeps the config in a repository instead (see below). Off while you have unsaved edits: save or discard them first |
| **Discard edits** | Throws your unsaved change away. Shown only while you have one |

A Project made before Project configs existed shows **No Project config yet**: Cloudgate generates
one for it when the instance is upgraded, and until then there is nothing to plan.

## Read a Plan

Each Environment's card is titled with its name. Its subtitle says where it stands: "Never
checked", "Open plan, checked" with a time (and, for a repository-kept config, the commit it read),
"Checked" for a Plan with nothing to do, or "Last plan applied" or "partly applied". With no open
Plan it says "No open plan. Check for changes to see what applying the config would do here."

- **Check for changes** makes a new Plan for that Environment from the config as it stands now.
- **Dismiss** drops the open Plan. It needs Environment update, which a read-only role lacks.

A Plan is made of these sections, each shown only when it has something in it:

| Section | What it lists |
|---|---|
| **Creates** | Services, and in a cloud the Environment network, that applying makes |
| **Existing databases** / **Existing buckets** | Databases and buckets made outside Cloudgate that the config uses as given, and what Cloudgate read about them |
| **Changes** | Settings that change on a Service, and Services rebuilt or redeployed with new settings |
| **Major upgrades** | A database moving to a new major version, such as `pg-main: 17 → 18`. A PostgreSQL is offline while it upgrades and a Redis may drop connections briefly; an upgrade cannot be undone. You type the Service's name to confirm |
| **Destroys** | Services the config no longer lists. You type each name to confirm |
| Drift | In a cloud, settings "Changed by hand in the AWS console" that Apply puts back |
| **Held builds** | Builds of Applications whose code and own config entry the same push changed: Apply builds them with the Plan's settings, Dismiss with the saved ones |
| **Results** | After an Apply, what each step did; the Plan as it was reviewed stays under **Show the Plan as it was reviewed** |
| **Notes** | What Cloudgate wants you to know about the Plan, such as a Template's parts held back in an Environment where that Template was never set up ([Templates](/docs/guide/templates#what-happens-in-the-projects-other-environments)), or the Same-machine warning (below) |

### Why does a Plan warn that a Service runs on Cloudgate's own machine?

On a self-hosted instance, each create in an Environment whose Deploy target is the machine
Cloudgate itself runs on (**This Cloudgate host**, or a Server whose address is that machine) gets
the Same-machine warning in the Plan's **Notes**: if that machine is lost, the Service and all of
Cloudgate's records go with it. It is a warning, not a refusal, and it cannot be hidden. A Service
the Environment already runs is not noted again. The Hosted instance never deploys to its own
machine, so its Plans never carry the note. See
[Projects and Environments](/docs/guide/projects-and-environments) for the Deploy target.

When the config already matches what runs, the card says so and there is nothing to apply. In a
cloud, each line can show the real resources it makes, with CPU, memory and a monthly total. A
deploy that stopped on drift opens the Plan with a line naming that Deployment.

### What does Apply do?

Apply runs each step in the Plan's order: the Environment network first, a Service a link reads
from before the Service that links to it, and a kind change's destroy right before its create.
Each step succeeds or fails on its own, so a Plan can end **partly applied**, with the results
saying which step failed. The button turns red when the Plan destroys or upgrades something, and
stays off until every name is typed. Its tooltip names what your role needs: Service create for
each create, Service update for each change, Service delete for each destroy, and Deployment
create. A role without one is refused before anything is written.

<Callout type="warn" title="Destroys cannot be undone">
A destroy asks you to type the Service's name. For a database, **Also delete the data of** skips
the final snapshot, and for a bucket, **Also delete the files of** empties it. Without the tick, a
bucket that holds files is kept with its volume and named in the results. Data and files deleted
this way are gone for good.
</Callout>

## Native settings for Swarm, AWS and Google Cloud

An entry the config describes can carry a `native` block with settings Cloudgate's own fields do
not cover, written in the platform's own spelling. Each value is laid over what Cloudgate writes
for the Service, never adds a resource, and shows as its own Plan line marked native.

```yaml
services:
  web:
    kind: web
    source: { folder: apps/web }
    native:
      docker:
        StopGracePeriod: 30000000000   # nanoseconds, as docker service inspect shows it
      aws:
        "aws_ecs_service.service":
          health_check_grace_period_seconds: 60
```

| Block | Where it applies | What it holds |
|---|---|---|
| `native.docker` | A Server | `Labels`, `HealthCheck`, `RestartPolicy`, `UpdateConfig`, `RollbackConfig`, `StopGracePeriod` and `Ulimits`, as the Docker Engine API takes them. A `cron` takes `Labels`, `StopGracePeriod` and `Ulimits`; a `bucket` takes `Labels` |
| `native.aws` | AWS | `hashicorp/aws` arguments, keyed by the OpenTofu address the Plan's cloud lines show, such as `"aws_db_instance.database"`. The ECS container is `"aws_ecs_task_definition.service".container_definitions`, in ECS's camelCase |
| `native.gcp` | Google Cloud | `hashicorp/google` arguments, keyed the same way, such as `"google_cloud_run_v2_service.service"` or `"google_sql_database_instance.database"` |

Every Plan checks every block on every Deploy target, so a typo shows on a Server's staging Plan
rather than on the first deploy to AWS. A refusal names the full path and the reason: an address
the entry's kind does not make, an argument the pinned provider does not have, an OpenTofu
meta-argument, or a [locked setting](/docs/glossary#locked-setting) such as `tags`, `region`,
labels in `traefik.*`, `com.docker.*` or `io.cloudgate.*`, or CPU and memory (use `size`). An exact
cloud size, such as an RDS instance class or a Cloud SQL tier, wins over `size`.

<Callout type="warn" title="Check custom Swarm settings before you apply">
  The config owns the seven Swarm settings whether or not `native.docker` is written: a key left
  out means Cloudgate's default for the kind. A described Service with custom Swarm settings saved
  and no block shows each one going back to its default, and applying that Plan resets them. Before
  you apply it, copy the values from the Service's Swarm settings into `native.docker`. A Cron
  service's saved health check, restart policy, update config or rollback config now fails its
  runs: clear them.
</Callout>

## Edit the config from a Project folder

A config kept in Cloudgate can also be edited as a file on your computer, with the
[CLI](/docs/cli#deploy-a-whole-project-from-one-folder). `cloudgate link --whole-project` makes the
folder a **Project folder** and downloads the config into it as `cloudgate.yaml`: a working copy.
Cloudgate keeps the config, never reads the working copy on its own, and the console still edits
it. The CLI adds `/cloudgate.yaml` to `.gitignore`, so the copy is never committed.

- `cloudgate config plan` sends the working copy as a Plan for each Environment, prints it and
  applies it on a yes. `cloudgate deploy` there does the same, then builds each app whose `source`
  is a `folder`.
- `cloudgate config pull` replaces the working copy with the current config.

An entry with `source: { folder: apps/web }` is built from that subfolder after the whole folder is
uploaded. Applying the Plan that creates such an app queues no Deployment: it waits for its first
upload, since there is nothing to build before one.

### What is the Config version?

Every Project config has a **Config version**, a counter that every Apply moves, a console **Save**
included. Storing the text it already holds moves nothing. A working copy remembers the version it
was downloaded at, and a Plan sent from it names that version. When the config has moved on since,
the Plan is refused with `CONFIG_VERSION_STALE`, saying when and by whom it changed, and nothing is
stored, so your copy never undoes a teammate's change. Pull, make your edits again, and plan.

<Callout type="limit" title="Cloudgate-kept configs only">
A Project whose config is kept in a repository cannot have a Project folder. Edit `cloudgate.yaml`
in the repository, or use **Move into Cloudgate** first.
</Callout>

## Keep the config in your repository

<Steps>
<Step title="Open the move dialog">
On the **Config** tab, press **Move to a repository**.
</Step>
<Step title="Choose where the file lives">

| Field | What it does | Notes |
|---|---|---|
| **Provider** | GitHub, GitLab, Gitea or Bitbucket | A custom git URL cannot keep the config |
| **GitHub connection** (or GitLab, ...) | The [git provider](/docs/guide/git-providers) connection to read through | Connections are set up under Settings, Git providers |
| **Repository** | The repository, from that connection's list | |
| **Path** | Where the file is | Empty means `cloudgate.yaml` or `cloudgate.yml` at the root (see below) |

<Screenshot name="project-config-move" alt="The Move the config into a repository dialog with GitHub and the northwind-labs connection chosen, and the Repository and Path fields below" caption="Choose where the file lives, then Preview each Environment's Plan before anything moves." />
</Step>
<Step title="Preview, then move">
Press **Preview**: the dialog shows what each Environment's Plan would be after the move, read from
its Config branch at a commit, with **Open the file**. Press **Move config**. Nothing is applied;
review each Plan, then apply it.
</Step>
</Steps>

### cloudgate.yaml or cloudgate.yml?

Either name works. With **Path** left empty, the move looks for `cloudgate.yaml`, then
`cloudgate.yml`, on each Environment's Config branch, and stores the name it found as the Project's
one path: later reads never switch to the other name. A branch that holds both uses
`cloudgate.yaml`, and the preview says the branch also has `cloudgate.yml`, which is not read. The
move is refused when different branches would need different names (set **Path** to the one to
use), or when a branch has neither.

Each Environment reads the file from its **Config branch** (Environment > **Settings**; empty means
the default branch), so `staging` can read `develop` while `production` reads `main`.

From then on, a push to the Config branch makes a Plan for that Environment, and **Check for
changes** makes one on demand. The **Project config** card says where the file is kept and which
connection reads it; builds and Preview deployments never read it. Each Environment's card shows its
copy read-only, with the branch and commit, **Open the file** and **Expand**. The console never
writes to your repository. If a copy cannot be read, that Environment's card says why.

<Callout type="note" title="If the connection is deleted">
When the git connection the config is read through is deleted, the card says no Environment can
read it. Press **Move to another repository** and choose a connection that reaches the repository.
</Callout>

### Move the config back into Cloudgate

Press **Move into Cloudgate**. **Keep the copy from** picks which copy becomes the config Cloudgate
keeps: **The default branch**, or an Environment, whose own Config branch is read. **Preview**
shows that copy and each Environment's Plan; **Move config** moves it. The repository is no longer
read, every Environment's Config branch is cleared, and the Config tab notes where it was moved out
of and when. Nothing is applied by the move.

<Callout type="limit" title="Repository-kept configs">
A config in a repository needs a connected git provider; a custom git URL cannot keep one. While
the config is in a repository, adding a new variable name in the console is refused: add it to
the file.
</Callout>

## Drift in a cloud

Drift is a change someone made by hand in the AWS or Google Cloud console. A Plan lists it on its
own. Applying always puts Cloudgate's version back (the button reads, for example, "Apply: put AWS
back"). A cloud change that finds drift stops before changing anything, and the drift becomes the
open Plan. To keep a hand change, write it into the config. See
[Cloud accounts](/docs/guide/cloud-accounts).

## Plan states

| State | Meaning |
|---|---|
| open | Waiting for Apply or Dismiss. One per Environment. |
| applied | Every step ran. |
| partly applied | Some steps ran; the results say which failed. |
| dismissed | Someone dropped it. |
| superseded | A newer Plan replaced it. |
| unchanged | The config matched what runs; nothing to do. |

A Plan whose commit or settings moved on since it was made is refused; make a new one.

A [Template](/docs/guide/templates) set up into an Environment adds its entries to that
Environment's Plan and waits as a **Pending setup** on the Environment's Services tab until you
apply it; its **Review the plan** button opens the Plan card here.

## Who can do what

| Action | Who |
|---|---|
| Read the config and **Check for changes** | Anyone who can read the Environment |
| **Save and plan** | Anyone who can read the Environments |
| **Dismiss** a Plan | Members with Environment update |
| **Apply** a Plan | Members who hold Service create, update or delete for each step, and Deployment create |
| Move the config to or from a repository | Owner, admin, or a custom role with Project update |

## What you cannot do

- A push never applies by itself; a person always presses **Apply**.
- An Agent can ask for a Plan but never applies or dismisses one.
- A field Cloudgate does not know refuses the Plan.
- The config never holds variable values, replica counts or per-Environment settings such as
  Domains and branches.
- One Service you may not change refuses the whole Apply.
